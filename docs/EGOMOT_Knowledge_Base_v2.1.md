# EGOMOT — Бизнес билим базасы v2.1

Версия: 2.1

Мурдагы версиялар: v1, v2 (29.08.2026)

## 1. Негизги принцип

Система мүмкүн болушунча жөнөкөй болушу керек.

Негизги бизнес цикли:

Капитал → Валюта сатып алуу → Кытайдан сатып алуу → Логистика → Складга приход → Сатуу → Акчанын кассага түшүшү → Кайра сатып алуу

Негизги талаптар:

- Телефондо ыңгайлуу иштеши керек.
- Ноутбукта толук иштеши керек.
- Келечекте Android жана iPhone тиркемелерине ылайыктуу архитектурада курулушу керек.
- Эң көп колдонулган Сатуу панели өтө жөнөкөй болушу керек.
- Принцип: бир экран — бир негизги тапшырма.
- Ар бир финансылык операция документ менен бекитилет.
- Акча жана товар калдыктары өз алдынча/түшүнүксүз өзгөрбөйт.
- Ар бир маанилүү өзгөрүүнүн аудит тарыхы сакталат.

Азырынча өзүнчө склад кызматкери жок.

Сатуучу негизги баа саясатын, кредиттик лимиттерди жана финансылык системанын глобалдык настройкаларын өзгөртө албайт.

## 3. Капитал

Системага капитал киргизүү мүмкүнчүлүгү болушу керек.

Капиталдын булагы:

- инвестордун капиталы;
- OWNER'дин өз капиталы;
- келечекте башка инвесторлор.

Ар бир капитал киргизүү өзүнчө Капитал документи (CAP) менен жүргүзүлөт жана кеминде төмөнкүлөрдү сактайт:

- документ номери;
- сумма;
- дата;
- валюта;
- керек болсо курс;
- капиталдын булагы (OWNER / кайсы инвестор);
- кайсы компаниялык эсепке акча кирди;
- документ/түшүндүрмө.

Инвестор акча кошсо же капитал кайтарылса, операциянын толук тарыхы сакталат.

Капитал киргенде компаниянын тиешелүү акча эсебинин балансы көбөйөт.

### 3.1. Ээсинин/инвестордун акча алуусу жана капиталды чыгаруу

Компаниядан OWNER же инвестор жеке максатта акча алганда, ал операция операциялык чыгым болуп эсептелбейт.

Негизги принцип:

Ээсинин же инвестордун компаниядан акча алуусу ОПУдагы чыгымды көбөйтпөйт жана бизнестин операциялык пайдасын азайтпайт. Ал капитал/equity кыймылы катары өзүнчө документтелет (WDW).

Система кеминде төмөнкү операцияларды айырмалайт:

- OWNER_WITHDRAWAL — OWNER жеке керегине компаниядан акча алат;
- INVESTOR_CAPITAL_RETURN — инвестор салган капиталдын бир бөлүгү же толугу менен кайтарылат;
- PROFIT_DISTRIBUTION — мурда табылган жана бөлүштүрүүгө жеткиликтүү пайда OWNER/инвесторго берилет.

#### 3.1.1. OWNER_WITHDRAWAL

OWNER компаниянын Cash / Bank / башка компаниялык эсебинен жеке керегине акча алса:

- тиешелүү акча эсеби азаят;
- Owner Equity / Capital тиешелүү эсепте азаят;
- операциялык чыгым түзүлбөйт;
- учурдагы ОПУдагы пайда өзгөрбөйт.

Мисал:

Компаниянын таза операциялык пайдасы — 200 000 сом. OWNER жеке керегине 80 000 сом алды.

Натыйжа:

- Cash ↓ 80 000 сом;
- Equity/Owner withdrawal тиешелүү тартипте азаят;
- ОПУдагы пайда = 200 000 сом бойдон калат.

80 000 сомду «Башка чыгым» катары жазууга болбойт.

#### 3.1.2. INVESTOR_CAPITAL_RETURN

Инвестор салган капиталын кайра алса:

- компаниянын Cash/Bank эсеби азаят;
- ошол инвесторго тиешелүү капиталдык баланс азаят;
- операциялык чыгым түзүлбөйт;
- ОПУдагы операциялык пайда өзгөрбөйт.

Система кайсы инвесторго, кайсы капиталдык салымга жана канча сумма кайтарылганын сактайт.

#### 3.1.3. PROFIT_DISTRIBUTION

OWNER же инвестор мурда табылган пайданын бир бөлүгүн алса, операция Profit Distribution катары жүргүзүлөт.

Ал:

- компаниянын акча эсебин азайтат;
- бөлүштүрүлбөгөн пайда / retained earnings же тиешелүү equity эсебин азайтат;
- учурдагы операциялык чыгым катары ОПУга кирбейт.

Капиталды кайтаруу менен пайданы бөлүштүрүү өзүнчө операциялар болуп сакталат.

#### 3.1.4. Withdrawal документи (WDW)

Ар бир капиталдык акча чыгарууда кеминде төмөнкүлөр сакталат:

- документ номери;
- дата жана убакыт;
- операция түрү;
- OWNER же инвестор;
- сумма;
- валюта;
- кайсы компаниялык эсептен акча чыкты;
- кайсы капитал/equity эсебине байланыштуу;
- максаты/комментарий;
- операцияны ким түздү;
- ким тастыктады;
- байланышкан капитал салымы же profit distribution негизи, эгер бар болсо.

#### 3.1.5. Отчетторго таасири

ОПУ / P&L: OWNER_WITHDRAWAL, INVESTOR_CAPITAL_RETURN жана PROFIT_DISTRIBUTION операциялык чыгым катары кирбейт.

ДДС / Cash Flow: Компаниядан реалдуу акча чыккандыктан cash outflow катары көрсөтүлөт, бирок операциялык расход категориясында эмес; капиталдык/финансылык агым катары өзүнчө көрсөтүлөт.

Баланс: Cash/Bank азаят жана тиешелүү Equity/Capital/Retained Earnings балансы азаят.

#### 3.1.6. Катуу тыюу

OWNER же инвестор жеке максатта алган акчаны төмөнкү категорияларга киргизүүгө болбойт:

- Other OPEX;
- склад арендасы;
- канцелярия;
- интернет;
- транспорт;
- айлык;
- башка операциялык чыгым.

Мындай акча алуу дайыма өзүнчө капиталдык документ (WDW) аркылуу жүргүзүлөт.

## 4. Кытайдан сатып алуу

### 4.1. Сатып алууну баштоо

Керектүү товарлардын/тетиктердин тизмесин OWNER түзөт (Purchase документи — PUR).

Кытайдагы өнөктөш:

- тизмени алат;
- товарларды чогултат;
- өзүнүн складында бир жүк/упаковка кылып даярдайт;
- жүктү Иу шаарындагы карго складына жөнөтөт.

Товар үчүн төлөм юань менен эсептелет.

Төлөм:

- толук;
- жарым-жартылай;
- толугу менен карыз

болушу мүмкүн.

Юань Кыргызстанда ортомчулардан сатып алынат (§10-А Валюта конвертация эрежеси боюнча документтелет) жана Кытайдагы өнөктөшкө:

- Alipay;
- WeChat;
- банктык карта/банктык канал

аркылуу жөнөтүлөт.

Поставщикке ар бир төлөм өзүнчө Supplier Payment (SPY) документи менен жүргүзүлөт жана кайсы валюталык кассадан чыкканы сакталат.

### 4.2. Поставщик боюнча төлөм статусу

Поставщик үчүн өзүнчө төлөм статусу:

- Төлөнө элек
- Жарым-жартылай төлөндү
- Толук төлөндү

Система поставщикке калган карызды CNY менен көрсөтөт. Карыздын KGS-эквиваленти отчеттордо reference rate менен маалымат катары көрсөтүлүшү мүмкүн, бирок карыздын өзү CNY менен жүргүзүлөт. Карыз жабылганда чыккан курстук айырма §10 боюнча өзүнчө статьяга түшөт.

### 4.3. Поставщикке алдын ала төлөм (Supplier Prepayment) — жаңы

Эгер SPY төлөмүнүн суммасы поставщикке болгон учурдагы ачык Payable'дан ашса, Supplier Payable терс болуп кетпейт.

Эреже:

- Payable'ды жапкан бөлүк — карызды азайтат;
- ашкан бөлүк — Supplier Prepayment / Поставщикке аванс (CNY менен) болуп өзүнчө эсептелет;
- кийинки Receipt тастыкталганда Prepayment автоматтык түрдө ошол приходдун төлөмүнө колдонулат;
- Prepayment да Supplier Receivable сыяктуу эле активдин статьясы жана §8.2деги курстук айырма логикасына баш ийет.

SPY документи кайсы бөлүгү карызды жапканын жана кайсы бөлүгү Prepayment болгонун так сактайт.

## 5. Логистика

### 5.1. Кытай ичиндеги транспорт

### 5.2. Эл аралык карго

Иу карго склады → Кыргызстандагы СВХ.

Карго негизинен доллар менен эсептелет.

Төлөм:

- доллар менен (USD валюталык кассадан);
- же сом менен

болушу мүмкүн.

Эгер сом менен төлөнсө, колдонулган доллар курсу сакталат. Эгер доллар сатып алынып, доллар менен төлөнсө, §10-А боюнча реалдуу сатып алуу/конвертация курсу сакталат.

Карго төлөм статусу:

- Төлөнө элек
- Жарым-жартылай төлөндү

Каргого карыз USD менен жүргүзүлөт. Ар бир карго төлөмү Cargo Payment (CPY) документи менен документтелет.

## 7. Товарды складга приход кылуу

Товар физикалык түрдө келип калганы сатууга даяр дегенди билдирбейт.

Приходго (Receipt — RCV) чейин партия боюнча керектүү маалыматтар толтурулушу керек:

- товар үчүн юань суммасы;
- колдонулган юань курсу (§10 эрежеси боюнча);
- Кытай ичиндеги транспорт;
- карго суммасы;
- карго валютасы;
- доллар курсу;
- Кыргызстандагы жергиликтүү транспорт;
- кайсы чыгым төлөнгөн;
- кайсы чыгым карыз;
- ар бир карыздын калдыгы.

Маалыматтар толук эмес болсо:

Приход кылууга жана товарды сатууга жол берилбейт.

Бардыгы толтурулуп, приход ырасталгандан кийин гана:

- товар складдын калдыгына кошулат;
- өздүк нарк (landed cost) эсептелет;
- товар сатууга ачылат.

Приход процессинин абалдары:

- Черновик
- Кабыл алууга даяр
- Приход болду
- Жабылды

## 8. Приходдогу расхождение жана анын финансылык натыйжасы

Приходдо заказ кылынган сан менен фактически кабыл алынган сан сөзсүз салыштырылат.

Мүмкүн болгон жыйынтык:

- так келди;
- жетпей келди (shortage);
- ашыкча келди (excess);
- келген товар бузулган/брак;
- айырманын себеби азырынча белгисиз.

Айырма болсо Расхождение актысы (DIF) милдеттүү түзүлөт.

Актта кеминде төмөнкүлөр сакталат:

- дата;
- Purchase / заказ номери;
- Receipt / приход;
- товар;
- заказ кылынган саны;
- фактически кабыл алынган саны;
- айырма;
- айырманын түрү жана пайда болгон этабы;
- жооптуу адам;
- комментарий;
- финансылык чечим;
- компенсация статусу.

### 8.1. Негизги финансылык принцип

Приход жана Inventory заказдагы сан боюнча эмес, фактически кабыл алынган сан боюнча таанылат. Жетпеген товарга төлөнгөн сумма кабыл алынган товарлардын өздүк наркына кошулбайт.

Мисал:

- заказ: 100 мотор × 1 000 сом = 100 000 сом;
- фактически келди: 90 мотор;
- жетишпейт: 10 мотор.

Эгер жетпеген 10 мотордун 10 000 сомдук наркын 90 моторго бөлүп салсак, алардын өздүк наркы жасалма көтөрүлөт. Мындай эсепке жол берилбейт.

Фактически келген товар: 90 × 1 000 = 90 000 сом → Inventory.

Жетпеген товар өзүнчө талап/эсептешүү катары жүргүзүлөт.

### 8.2. Поставщикке алдын ала төлөнгөн shortage

Эгер жетпеген товар үчүн поставщикке акча мурда төлөнгөн болсо, ошол сумма:

Supplier Receivable / Поставщиктин дебитордук карызы

катары эсептелет.

Supplier Receivable CNY менен сакталат. Ал жабылганда (компенсация, акча кайтаруу же списание) чыккан курстук айырма §10 статьясына түшөт.

Ал сумма:

- Inventory'ге кирбейт;
- келген товарлардын landed cost'ун көбөйтпөйт;
- чыгым катары дароо таанылбайт;
- поставщиктен алынуучу товар/акча талабы болуп калат.

### 8.3. Поставщикке али төлөнбөгөн shortage

Эгер жетпеген товар үчүн акча али төлөнө элек болсо, система жасалма Supplier Receivable түзбөйт.

Анын ордуна:

Supplier Payable жетпеген товарга тиешелүү суммага азайтылат.

Демек:

- алдын ала/ашыкча төлөнгөн бөлүк → Supplier Receivable;
- төлөнө элек бөлүк → Supplier Payable азаят.

### 8.4. Расхождениенин пайда болгон этабы

Минималдуу түрлөр:

- SUPPLIER_SHORTAGE — поставщик аз жөнөткөн;
- CARGO_LOSS — эл аралык каргодо жоголгон;
- LOCAL_TRANSPORT_LOSS — Кыргызстандагы транспортто жоголгон;
- RECEIVING_DAMAGE — товар келди, бирок кабыл алууда бузулган/брак деп табылды;
- UNKNOWN — себеп азырынча аныктала элек.

UNKNOWN кийин териштирүү бүткөндө туура түргө өзгөртүлөт; өзгөртүү аудитте сакталат.

RECEIVING_DAMAGE товардын жолу (v2.1де такталды): кабыл алууда брак деп табылган товар физикалык кабыл алынса, ал өзүнүн эсептелген landed cost'у менен түз DEFECT складга кирет — MAIN'ге эч качан тийбейт жана Available for Sale'га кирбейт. Андан ары ал Claim (§8.5) же списание (§38) процесси менен жүргүзүлөт.

### 8.5. Claim / Талап механизми (жаңы)

Жооптуу тараптан талап кылынуучу ар бир жоготуу үчүн өзүнчө Claim документи (CLM) түзүлөт.

Claim түрлөрү:

- SUPPLIER_CLAIM — поставщикке талап (shortage, брак, ката товар боюнча). CNY менен жүргүзүлөт;
- CARGO_CLAIM — карго компаниясына талап (CARGO_LOSS боюнча). USD же келишим валютасы менен жүргүзүлөт.

CARGO_CLAIM суммасына кеминде төмөнкүлөр кирет:

- жоголгон товардын поставщикке төлөнгөн наркы;
- жоголгон товарга тиешелүү, фактически төлөнгөн логистикалык чыгымдардын үлүшү.

Claim статустары: OPEN, UNDER_REVIEW, PARTIALLY_COMPENSATED, COMPENSATED, WRITTEN_OFF, CLOSED.

Claim компенсацияланбай калса, OWNER чечими менен WRITTEN_OFF болуп, сумма өзүнчө «Логистикалык/поставщик жоготуулары» статьясы менен чыгымга таанылат. Бул чыгым сатуучулардын бонус базасына кирбейт.

Ар бир Claim баштапкы Расхождение актысына (DIF) байланышат.

### 8.6. Логистикалык чыгымдарды кайра бөлүштүрүү

Жалпы эреже боюнча allocation фактически кабыл алынган товарларга жүргүзүлөт жана §9дагы WEIGHT / VOLUME / VALUE / MANUAL эрежелерин колдонот.

Бирок чыгымдын фактически пайда болгон этабы эске алынат:

- поставщик 100дүн ордуна 90 товар гана жөнөткөн болсо, тиешелүү транспорттук allocation фактически жөнөтүлгөн/кабыл алынган товарларга негизделет;
- эгер 100 товар чындап карго менен ташылып, жолдо 10 товар жоголсо, фактически болгон карго чыгымы автоматтык түрдө калган 90 товарга жөн эле кайра жүктөлбөйт;
- жоголгон товарга тиешелүү реалдуу чыгымдар CARGO_CLAIM аркылуу жооптуу тарапка талап катары жүргүзүлөт (§8.5).

Ошондуктан система shortage болгондо бардык чыгымдарды сокур түрдө кайра бөлүштүрбөйт; расхождениенин этабы жана чыгымдын экономикалык маңызы эске алынат.

### 8.7. Кийинки партияда компенсация

Эгер Кытайдагы поставщик/партнёр жетпеген же брак товарды кийинки партияга кошуп берсе:

- компенсация кайсы баштапкы Расхождение актысына / Claim'ге тиешелүү экени көрсөтүлөт;
- Supplier Receivable / Claim тиешелүү суммага азайтылат же жабылат;
- компенсацияланган товар жаңы Receipt аркылуу кабыл алынат;
- товар жаңы LOT / FIFO cost layer катары складга кирет;
- ошол жаңы жеткирүүгө тиешелүү реалдуу логистикалык чыгымдар анын landed cost'уна кошулат;
- баштапкы расхождение/Claim статусу толук же жарым-жартылай компенсацияланды деп жаңыланат.

Компенсация тарыхы баштапкы shortage/Claim менен дайыма байланышта сакталат.

### 8.8. Excess — ашыкча келген товар

Ашыкча товар автоматтык түрдө акысыз товар же киреше деп эсептелбейт.

OWNER/жооптуу кызматкер анын себебин тактайт:

- поставщиктин катасы;
- бонус/акысыз товар;
- документке кирбей калган сатып алуу;
- башка себеп.

Финансылык чечим такталмайынча excess боюнча маалымат Расхождение актысында ачык бойдон сакталат. Товарды складга кабыл алуу жана анын өздүк наркын бекитүү документтелген чечимге ылайык жүргүзүлөт.

### 8.9. Расхождение статусу

Расхождение үчүн кеминде төмөнкү статустар колдонулат:

- OPEN;
- UNDER_REVIEW;
- PARTIALLY_COMPENSATED;
- COMPENSATED;
- WRITTEN_OFF;
- CLOSED.

Расхождение документин жөн гана өчүрүүгө болбойт. Бардык компенсация, карызды азайтуу, акча кайтаруу жана списание операциялары баштапкы актка байланышат.

## 9. Логистикалык чыгымдарды бөлүштүрүү (Allocation)

Логистикалык жана башка түз партиялык чыгымдар товарлардын landed cost'уна негиздүү allocation аркылуу кошулат.

### 9.1. SKU салмагы — милдеттүү маалымат

Ар бир SKU үчүн физикалык салмак (weightKg) милдеттүү талаа болуп эсептелет.

Эгер приходдогу бир да товарда физикалык салмак жок болсо:

Приходду тастыктоого болбойт: товарлардын салмак маалыматтары толук эмес.

Демек, салмагы жок SKU бар партияда приход блоктолот.

Салмак кийин FIFO, логистика анализи жана өздүк наркты текшерүү үчүн да сакталат.

### 9.2. Allocation basis партияга эмес, ар бир чыгымга тандалат

Бир партиядагы бардык чыгымдарды бир эле формула менен бөлүштүрүү милдеттүү эмес.

Ар бир түз чыгым өзүнүн Allocation Basis параметрин сактайт.

Колдоого алынуучу негизги варианттар:

- WEIGHT — физикалык салмак боюнча (демейки);
- VOLUME — көлөм же көлөмдүк/chargeable weight боюнча;
- VALUE — товардын сатып алуу наркы боюнча;
- MANUAL — OWNER тарабынан түз бөлүштүрүү.

Мисал:

| Чыгым | Allocation Basis |
|---|---|
| Кытай ички транспорту | WEIGHT |
| Yiwu → Кыргызстан Cargo | VOLUME (эгер карго көлөмдүк салмак менен эсептесе) |
| Кыргызстан ички транспорту | WEIGHT |
| Наркка байланышкан камсыздандыруу/комиссия | VALUE |
| Карго даяр бөлүштүрүлгөн сумма берсе | MANUAL |

Баштапкы версия (MVP) эскертүүсү: Баштапкы этапта WEIGHT жана MANUAL жетиштүү. VOLUME параметр катары системада каралат, бирок карго чын эле көлөмдүк салмак менен эсептеген учурда гана активдештирилет.

### 9.3. WEIGHT формуласы

Товарга бөлүнгөн чыгым = Жалпы чыгым × Товар позициясынын жалпы физикалык салмагы / Партиянын жалпы физикалык салмагы

Товар позициясынын жалпы салмагы: 1 даана салмак × кабыл алынган саны.

### 9.4. VOLUME / көлөмдүк салмак

Жеңил, бирок көлөмдүү товарлар үчүн физикалык салмак өздүк наркты бурмалап коюшу мүмкүн (пластик капкактар, зеркало, сиденье, чоң жеңил кузов деталдары).

Эгер карго көлөмдүк салмак же chargeable weight менен эсептесе, ошол cargo чыгымы VOLUME базасы менен бөлүштүрүлөт.

SKU үчүн зарыл учурда: узундук, туурасы, бийиктиги, көлөм, көлөмдүк салмак же карго берген chargeable weight сакталат.

Көлөмдүк салмактын коэффициенти системага катуу жазылбайт; ал карго компаниясына же конкреттүү cargo expense'ке жараша конфигурацияланат.

Эгер чыгым үчүн VOLUME тандалса, бирок керектүү көлөм/chargeable weight маалыматтары толук эмес болсо, приход тастыкталбайт.

### 9.5. VALUE формуласы

Товарга бөлүнгөн чыгым = Жалпы чыгым × Товар позициясынын сатып алуу наркы / Партиянын жалпы сатып алуу наркы

Наркка байланышкан камсыздандыруу же комиссия үчүн колдонулушу мүмкүн.

### 9.6. MANUAL allocation

Эгер поставщик, карго же башка тарап чыгымды товарлар боюнча даяр бөлүп берсе, OWNER MANUAL режимин колдоно алат.

MANUAL режиминде:

- ар бир LOT Item'га бөлүнгөн сумма көрсөтүлөт;
- бөлүштүрүлгөн суммалардын жалпысы expense суммасына так барабар болушу керек;
- айырма болсо приход тастыкталбайт;
- ким кол менен бөлүштүргөнү аудитте сакталат.

### 9.7. Landed cost'ко кошулуу

Ар бир түз чыгым өзүнүн allocation basis'и менен LOT Items арасында бөлүштүрүлгөндөн кийин гана акыркы landed cost эсептелет.

Жалпы логика:

Purchase Cost + Allocated Direct Expenses = LOT Item Total Landed Cost

LOT Item Total Landed Cost / Received Qty = Unit Landed Cost

Ушул Unit Landed Cost FIFO cost layer'дин өздүк наркы болуп бекитилет.

### 9.8. Өзгөрбөс validation эрежелери

Приход төмөнкү учурларда блоктолот:

- партиядагы кандайдыр бир SKUда физикалык салмак жок;
- WEIGHT allocation үчүн керектүү салмак маалыматтары толук эмес;
- VOLUME тандалып, керектүү көлөм/chargeable weight маалыматтары толук эмес;
- VALUE үчүн сатып алуу наркы толук эмес;
- MANUAL allocation суммасы expense'тин жалпы суммасына барабар эмес;
- allocation бүткөн эмес жана акыркы landed cost эсептелген эмес.

### 9.9. Allocation Rounding — тегеректөө жана тыйын калдыгы

Allocation процессинде ашыкча же кем тыйынга жол берилбейт.

Σ Allocated Amount = Source Expense Amount

Ар бир чыгым боюнча SKU/LOT Item'дарга бөлүнгөн суммалардын жыйынтыгы баштапкы чыгымга 0.01 KGS тактыкта так тең болушу керек.

Эсептөө тартиби:

1. WEIGHT / VOLUME / VALUE allocation ички эсептөөдө жогорку тактык менен эсептелет.
2. Финалдык акча суммалары 0.01 KGS тактыкка тегеректелет.
3. Система Remainder = Source Expense Amount − Σ Rounded Allocations эсептейт.
4. Remainder нөл эмес болсо, ал эң чоң allocation алган позицияга кошулат же андан алынат.
5. Эгер эң чоң allocation боюнча позициялар тең болсо, документтеги туруктуу тартип боюнча биринчи позиция тандалат.
6. Σ Final Allocated Amount = Source Expense Amount так аткарылмайынча документ тастыкталбайт.

Мисал: 1 000.00 KGS чыгымдын финалдык allocation'у 333.34 + 333.33 + 333.33 = 1 000.00 KGS болушу керек. 999.99 же 1 000.01 KGS кабыл алынбайт.

Бул эреже бардык landed-cost allocation'дарга, анын ичинде MANUAL режимине да колдонулат.

## 10. Валюта жана курстук айырма

### 10.1. Приход курсунун булагы (такталды)

Приход учурунда ар бир чыгым позициясы үчүн курс так эреже менен аныкталат:

1. Төлөнгөн бөлүк: ошол төлөмдө фактически колдонулган валюта сатып алуу курсу (§10-А FIFO валюта кассасы боюнча).
2. Карыз бөлүк (төлөнө элек): акыркы реалдуу валюта сатып алуу курсу — reference rate. Эгер система иштегенден бери валюта сатып алуу боло элек болсо, OWNER кол менен reference rate киргизет жана бул аудитте сакталат.

Приход документи колдонулган ар бир курсту жана анын булагын (ФАКТИЧЕСКИЙ / REFERENCE / MANUAL) сактайт.

### 10.2. Курстук айырма

Ошол курс менен товар складга кирип, өздүк наркы бекитилет.

Мисалы:

- приходдо: юань 13.00 KGS; доллар 87.80 KGS;
- кийин реалдуу төлөм күнү: юань 13.50; доллар 88.00.

Айырма товарлардын бекитилген өздүк наркын кайра өзгөртпөйт.

Айырма өзүнчө финансылык статьяга түшөт:

Валюталык курстук пайда/чыгым (FX Gain/Loss)

Система көрсөтөт:

- приходдогу курс;
- төлөмдөгү реалдуу курс;
- айырма;
- сом менен пайда/чыгым.

FX Gain/Loss сатуучулардын бонус базасына кирбейт (§23.5).

## 10-А. Валюта конвертация модулу (жаңы)

### 10-А.1. Валюталык кассалар

Компанияда KGS эсептеринен тышкары өзүнчө валюталык кассалар жүргүзүлөт:

- CNY Cash — юань кассасы;
- USD Cash — доллар кассасы;
- зарыл болсо валюталык банк/электрондук эсептер.

Ар бир валюталык касса өз валютасында баланс жүргүзөт.

### 10-А.2. Currency Exchange документи (CEX)

KGS менен валюта сатып алуу (же тескерисинче) өзүнчө Currency Exchange (CEX) документи менен документтелет:

- документ номери;
- дата жана убакыт;
- берилген валюта жана сумма (мис. KGS 130 000);
- алынган валюта жана сумма (мис. CNY 10 000);
- фактический курс (13.00);
- ортомчу/булак;
- кайсы эсептен акча чыкты;
- кайсы валюталык кассага акча кирди;
- комиссия, эгер бар болсо;
- операцияны ким жүргүздү;
- комментарий.

Тескери багыт (v2.1де такталды): валюта кайра KGSке сатылса (CNY/USD → KGS), сатылган валюта FIFO боюнча эң эски катмардан чыгарылат. Алынган KGS менен ошол катмарлардын сатып алуу наркынын (KGS менен) айырмасы FX Gain/Loss статьясына түшөт (§10.2) жана бонус базасына кирбейт.

### 10-А.3. Валюталык кассадагы FIFO

Валюталык кассанын KGS-наркы FIFO принциби менен жүргүзүлөт: ар бир CEX операциясы өзүнүн курсу менен өзүнчө катмар (layer) түзөт.

Валюталык кассадан төлөм чыкканда (SPY, CPY) эң эски катмардагы валюта биринчи чыгарылат жана ошол катмардын сатып алуу курсу «фактический курс» катары колдонулат.

Мисал:

- CEX-1: 10 000 CNY × 13.00 = 130 000 KGS;
- CEX-2: 5 000 CNY × 13.40 = 67 000 KGS;
- Поставщикке төлөм: 12 000 CNY.

FIFO боюнча: 10 000 × 13.00 + 2 000 × 13.40 = 156 800 KGS — ушул сумма төлөмдүн KGS-наркы болот.

### 10-А.4. Катуу эреже

Валюта кассасынын балансы терс боло албайт. Кассада жетишсиз валюта болсо, төлөм документи тастыкталбайт — алгач CEX жүргүзүлөт.

Валюта алмаштыруу эч качан «башка чыгым» же түшүнүксүз кыймыл катары жазылбайт; дайыма CEX документи менен жүрөт.

## 11. Кардарлар

Кардарлардын негизги типтери:

- Оптовый
- Розничный
- Мастер

### 11.1. Walk-in Customer — идентификацияланбаган чекене кардар

Walk-in Customer конкреттүү бир адамдын жеке карточкасы эмес. Ал аты-жөнү/телефону боюнча катталбаган кадимки чекене сатуулар үчүн колдонулган жалпы техникалык Customer.

Walk-in Customer'ге сатуу 100% толук төлөм менен гана жүргүзүлөт. Debt, Credit Limit, Reservation/Advance жана жеке Customer Category колдонулбайт.

#### 11.1.1. Уруксат берилет

Walk-in Customer аркылуу:

- кадимки чекене Sale түзүүгө;
- Cash / MBank / O!Bank / башка уруксат берилген ыкма менен толук төлөм алууга;
- mixed payment колдонууга;
- чек/сатуу документин түзүүгө;
- Original Sale табылган учурда возврат жүргүзүүгө болот.

#### 11.1.2. Тыюу салынат

Walk-in Customer үчүн:

- карызга сатууга;
- жарым-жартылай төлөнгөн Sale калтырууга;
- Credit Limit коюуга;
- Reservation / бронь түзүүгө;
- Advance / аванс кабыл алууга;
- Standard / Silver / Gold / VIP категориясын эсептөөгө;
- жеке лоялдуулук артыкчылыктарын топтоого болбойт.

Walk-in Sale тастыкталышы үчүн: Outstanding Amount = 0 болушу милдеттүү.

#### 11.1.3. Сатып алуу тарыхы

Walk-in аркылуу жасалган бардык сатуулар бир конкреттүү адамдын сатып алуу тарыхы болуп эсептелбейт. Walk-in'дин жалпы обороту Customer Category, VIP/Silver/Gold статусу, жеке Credit Limit же жеке кардар аналитикасы үчүн колдонулбайт.

#### 11.1.4. Walk-in возврат (v2де такталды)

Walk-in Customer үчүн возврат мүмкүн, бирок сөзсүз конкреттүү Original Sale менен байланышат — эч кандай exception жок.

Original Sale табылбаса, возврат системада жүргүзүлбөйт. Бул эреже OWNER үчүн да колдонулат.

Возврат original selling price, quantity, FIFO LOT Allocation/cost жана original payment source боюнча §35теги жалпы Return эрежелерине ылайык жүргүзүлөт.

Сатуу документин табуу үчүн чек номери, дата, товар жана сумма боюнча издөө болушу керек.

#### 11.1.5. Кардарды качан каттоо керек?

Эгер кардарга төмөнкүлөрдүн бири керек болсо, өзүнчө Customer Card түзүлөт:

- карызга сатып алуу;
- бронь;
- аванс;
- жеке сатып алуу тарыхы;
- Customer Category;
- Credit Limit;
- туруктуу кардар аналитикасы.

Кардар кийин катталса, мүмкүн болгон учурда мурдагы конкреттүү Walk-in Sale'дарды документтелген жана аудиттелген тартипте анын Customer Card'ына байланыштырууга болот.

## 12. Кардардын категориялары

Кардардын тибинен тышкары категориясы болот.

Баштапкы категориялар:

- Standard
- Silver
- Gold
- VIP

Баштапкы мисал:

- Standard: 0–49 999 KGS
- Silver: 50 000–99 999 KGS
- Gold: кийин такталат
- VIP: кийин такталат

Порогдор системада настройка аркылуу өзгөртүлөт.

### 12.1. Категорияны эсептөө эрежеси (v2де такталды)

Категория кардардын сатып алуу көлөмүнө жараша автоматтык эсептелет:

- эсептөө мезгили: rolling акыркы 12 ай (параметр, OWNER өзгөртө алат);
- эсепке тастыкталган Sale суммалары минус возвраттар кирет;
- аванс жана бронь өзүнчө эсепке кирбейт — сатуу тастыкталганда гана эсептелет;
- категория ай сайын автоматтык кайра эсептелет (параметр);
- көлөм азайса категория төмөндөшү мүмкүн;
- OWNER конкреттүү кардарга кол менен категория коё алат (Manual Override) — бул аудитте сакталат жана автоматтык эсептөөдөн жогору турат.

## 12-А. Warehouse — склад өз алдынча негизги объект

Склад системада өз алдынча master-data объект болуп эсептелет.

Негизги архитектура:

Company / Business Entity → Warehouse → LOT → LOT Items → Stock

Баштапкы этапта кеминде төмөнкү складдар болушу керек:

- MAIN — негизги сатылуучу товарлар кампасы;
- DEFECT — брак, кайтарылган же сатууга жараксыз товарлар кампасы.

Кийин архитектураны өзгөртпөстөн төмөнкү склад түрлөрүн кошууга болот: SERVICE, TRANSIT, BRANCH, OTHER.

### 12-А.1. Warehouse карточкасы

Ар бир Warehouse кеминде: Warehouse ID; уникалдуу Warehouse Code; аталышы; Warehouse Type; дареги/жайгашкан жери; жооптуу кызматкер; Active/Inactive статусу; Company/Business Entity байланышы; комментарий; createdAt/updatedAt.

Warehouse Code уникалдуу болушу керек.

### 12-А.2. Stock Balance деңгээли

Товардын калдыгы компания боюнча бир гана жалпы сан катары сакталбайт.

Негизги stock balance деңгээли:

Product + Warehouse + LOT

Мисал:

- Мотор 1800W / MAIN / LOT-005 = 8 даана;
- Мотор 1800W / DEFECT / LOT-003 = 2 даана.

Компания боюнча физикалык жалпы саны 10 болушу мүмкүн, бирок сатууга жеткиликтүү саны MAIN складындагы эрежеге ылайык эсептелет.

DEFECT складындагы товарлар Available for Sale'га кирбейт.

### 12-А.3. Warehouse Type

Минималдуу тизме: MAIN, DEFECT, SERVICE, TRANSIT, BRANCH, OTHER. Баштапкы версияда MAIN жана DEFECT жетиштүү.

### 12-А.4. Warehouse Transfer / Перемещение (TRF)

Складдар ортосунда товарды түз stock санын өзгөртүү менен жылдырууга болбойт.

Ар бир ички которуу өзүнчө Warehouse Transfer (TRF) документи аркылуу жүргүзүлөт.

Transfer документинде кеминде: документ номери; дата; From Warehouse; To Warehouse; Product; LOT; Qty; Unit FIFO Cost; Total Cost; жөнөткөн кызматкер; кабыл алган кызматкер; статус; комментарий; createdAt/confirmedAt.

Минималдуу статус: DRAFT, SENT, RECEIVED, CANCELLED.

### 12-А.5. FIFO cost ички перемещениеде өзгөрбөйт

Компаниянын өз складдарынын ортосундагы Warehouse Transfer: сатуу эмес, сатып алуу эмес, киреше эмес, операциялык чыгым эмес.

Товар баштапкы FIFO cost layer менен көчөт. Мисалы, MAIN'деги LOT Unit Cost = 7 500 сом болсо, MAIN → SERVICE же MAIN → DEFECT которулганда жаңы складдагы ошол LOT cost = 7 500 сом бойдон калат.

### 12-А.6. DEFECT складга которуу

Брак же сатууга жараксыз товар нормалдуу MAIN stock'ко аралашпайт. Керек болсо MAIN → DEFECT Warehouse Transfer же Return/Defect процесси аркылуу жүргүзүлөт.

DEFECT складындагы товар: Available Stock'ко кирбейт; кадимки Sale'да сатылбайт; өзүнчө defect/write-off процесси менен башкарылат.

### 12-А.7. Келечектеги филиалдар

Warehouse башынан Company / Business Entity менен байланышкандыктан, кийин филиал складдарын кошууга болот (HQ MAIN, Osh BRANCH, Jalal-Abad BRANCH). Эгер келечекте филиал өзүнчө юридикалык же финансылык entity болсо, ошол учурда intercompany/branch transfer логикасы бөлүнөт. Баштапкы версияда филиалдык татаал эсеп киргизилбейт, бирок Warehouse модели ага тоскоол болбой тургандай курулат.

### 12-А.8. Warehouse боюнча катуу эрежелер

1. Ар бир складдык кыймыл конкреттүү Warehouse'ка байланышат.
2. Stock Product + Warehouse + LOT деңгээлинде жүргүзүлөт.
3. Stock кол менен түз өзгөртүлбөйт.
4. Складдар ортосундагы кыймыл Warehouse Transfer документи менен гана жүргүзүлөт.
5. Ички Warehouse Transfer FIFO cost'ту өзгөртпөйт.
6. DEFECT складындагы товар Available for Sale'га кирбейт.
7. Warehouse Inactive болсо, жаңы кыймылга колдонулбайт.
8. Stock эч качан терс боло албайт; жетишсиз калдыкта сатуу/трансфер блоктолот.
9. Келечектеги жаңы склад/филиал үчүн жаңы Warehouse түзүлөт; негизги inventory архитектурасы кайра курулбайт.

## 12-Б. Product Master — товар карточкасынын структурасы

Товар карточкасы системанын негизги master-data объекттеринин бири. Ар бир товар бир жолу түзүлүп, сатып алуу, LOT/FIFO, склад, сатуу, баа, отчет процесстеринде ошол эле Product ID аркылуу колдонулат.

### 12-Б.1. Негизги маалымат

Ар бир Product Card кеминде: SKU Code (уникалдуу ички товар коду); аталышы; категория; бренд/өндүрүүчү; өлчөө бирдиги (даана, комплект, метр ж.б.); barcode/штрихкод; OEM/Factory Part Number; кыскача сүрөттөмө; товар сүрөтү/сүрөттөрү; Active/Inactive статусу.

Ар бир активдүү товарда уникалдуу SKU Code болушу керек. Бир SKU бир гана Product'ка тиешелүү болот.

### 12-Б.2. Альтернативдүү аталыштар жана издөө

Бир эле тетик рынокто, мастерлерде жана Кытайдагы поставщикте ар башка ат менен аталышы мүмкүн. Ошондуктан товарга кошумча: альтернативдүү аталыштар; орусча/кыргызча аталыштар; кытайлык/поставщик колдонгон аталыш; OEM/Factory code; издөө keywords байланыштырылышы мүмкүн.

Product Search SKU, аталыш, barcode, OEM code жана альтернативдүү аталыштар боюнча иштейт.

### 12-Б.3. Физикалык маалымат

Ар бир SKU үчүн: weightKg — милдеттүү; length; width; height; volume; зарыл болсо volumetric/chargeable weight маалыматтары сакталат.

Length/width/height бардык товар үчүн милдеттүү эмес, бирок §9 боюнча VOLUME allocation колдонулган учурда керектүү көлөм маалыматтары толук болушу керек.

WeightKg жок товар менен приход тастыкталбайт.

### 12-Б.4. Складдык маалымат

Product Card'да система автоматтык көрсөтөт: Current Stock; Reserved Stock; Available Stock; Minimum Stock; Reorder Point; Inbound Qty; активдүү FIFO LOT'тор; ар бир LOT боюнча Remaining Qty жана Unit Landed Cost.

Available Stock = Current Stock − Reserved Stock

Minimum Stock жана Reorder Point OWNER тарабынан настройкаланат.

Current Stock, Reserved Stock жана FIFO Cost кол менен түз редакцияланбайт. Алар складдык документтерден, резервдерден жана LOT/FIFO кыймылдарынан эсептелет.

### 12-Б.5. Сатып алуу маалыматы

Product Card'да: негизги Supplier; Supplier Product Code; акыркы сатып алуу баасы; сатып алуу валютасы; CNY price history; акыркы сатып алуу датасы; акыркы receipt датасы сакталат/көрсөтүлөт.

Акыркы сатып алуу баасын өзгөртүү мурдагы FIFO LOT'тордун бекитилген landed cost'ун өзгөртпөйт.

### 12-Б.6. Сатуу жана баа маалыматы

Product Card pricing policy менен байланышат. Көрсөтүлүшү мүмкүн: base markup; Type × Category pricing; сунушталган сатуу баалары; Minimum Selling Price; скидка чеги; учурдагы FIFO cost; күтүлгөн margin.

Кадимки Sale үчүн §13төгү скидка жана FIFO COGSтен төмөн сатууга тыюу эрежелери колдонулат.

### 12-Б.7. Кепилдик параметри (жаңы)

Product Card'да же товар категориясында:

- Warranty Days — кепилдик мөөнөтү (күн менен, OWNER настройкасы);
- кепилдик шарттарынын кыскача сүрөттөмөсү.

§36-А боюнча брак возврат ушул параметрге таянат.

### 12-Б.8. Совместимость (баштапкы версияда жөнөкөйлөтүлдү)

Баштапкы версияда (MVP): Product Card'да жөнөкөй Compatibility Notes текст талаасы жүргүзүлөт (кайсы трицикл моделдерине туура келери жазылат) жана издөөгө кирет.

Кийинки фазада (Приоритет 3): структураланган Product ↔ Vehicle Model many-to-many байланышы, VERIFIED/UNVERIFIED статустар жана модель боюнча тетик фильтри киргизилет. Database архитектурасы буга даяр болуп курулат, бирок MVP функционалына кирбейт.

### 12-Б.9. Product Master боюнча катуу эрежелер

1. Ар бир активдүү Product уникалдуу SKU Code'го ээ.
2. WeightKg приход үчүн милдеттүү.
3. Current Stock кол менен өзгөртүлбөйт.
4. FIFO LOT Cost Product Card'дан кол менен өзгөртүлбөйт.
5. Stock өзгөрүүсү документтелген складдык операция аркылуу гана жүргүзүлөт.
6. Product Search SKU, аталыш, barcode, OEM/Factory code жана альтернативдүү аталыштарды колдойт.

## 13. Баа түзүү

Баанын логикасы эки деңгээлдүү:

- товарга негизги наценка;
- кардардын тибине жана категориясына жараша кошумча наценка.

Мисалы: Оптовый VIP — кошумча наценка 0% болушу мүмкүн; Standard кардарга кошумча наценка жогору болушу мүмкүн.

Так пайыздардын баары OWNER тарабынан настройкадан өзгөртүлөт.

Кардар тандалгандан кийин система: типти, категорияны, ошол кардарга тиешелүү сатуу баасын автоматтык чыгарат.

### 13.1. Скидка берүү укугу

Система кардардын Type + Category жана товар боюнча бекитилген pricing policy негизинде сунушталган сатуу баасын автоматтык чыгарат.

Скидка кол менен берилсе, система сөзсүз текшерет:

- кызматкердин скидка берүүгө укугу;
- кызматкер үчүн уруксат берилген Max Discount %;
- скидкадан кийинки Final Selling Price;
- сатууга тиешелүү FIFO COGS;
- Minimum Selling Price;
- OWNER approval талап кылынабы.

SALES MANAGER OWNER белгилеген лимиттин ичинде гана скидка бере алат.

### 13.2. Minimum Selling Price

Кадимки сатууда товарды экономикалык жактан негизсиз төмөн баада сатууга жол берилбейт.

Минималдуу чек эки контролдон турат:

- OWNER/pricing policy койгон Minimum Selling Price;
- сатылып жаткан конкреттүү санга эсептелген FIFO COGS.

Final Selling Price ушул талаптардан төмөн болбошу керек.

### 13.3. FIFO негизиндеги минималдуу чек

FIFO колдонулгандыктан, өздүк нарк Product карточкасындагы акыркы же орточо баа менен текшерилбейт.

Система сатуу тастыкталганга чейин кайсы LOT'тордон канча товар чыгаарын симуляциялайт жана ошол сатууга тиешелүү FIFO COGSти эсептейт.

Мисал:

LOT-1: 5 даана × 7 000 сом; LOT-2: 5 даана × 7 500 сом; сатуу: 10 даана.
FIFO COGS: 5 × 7 000 + 5 × 7 500 = 72 500 сом.

Демек, кадимки сатууда 10 даананын скидкадан кийинки жалпы Final Selling Price'ы FIFO COGSтен төмөн боло албайт.

### 13.4. Өз наркынан төмөн сатууга катуу блок

Кадимки SALE ичинде скидкадан кийинки Final Selling Price сатууга тиешелүү FIFO COGSтен төмөн боло албайт.

Бул блокту: SALES MANAGER айланып өтө албайт; башка кадимки кызматкер айланып өтө албайт; OWNER да кадимки Sale ичинде override кылбайт.

Система мындай операцияны тастыктоого жол бербейт.

### 13.5. OWNER Approval талап кылынган скидка

Эгер SALES MANAGER'дин Max Discount % лимитинен чоң скидка керек болсо, операция OWNER APPROVAL талап кылат.

OWNER: сунушталган бааны; скидка суммасын жана пайызын; FIFO COGSти; күтүлгөн маржаны; скидканын себебин көрүп туруп гана бекитет же четке кагат.

Бирок OWNER approval кадимки Sale'да FIFO COGSтен төмөн сатууга уруксат бербейт.

### 13.6. LOSS SALE / LIQUIDATION (LSS)

Эгер бизнес үчүн атайын өздүк нарктан төмөн сатуу зарыл болсо, ал кадимки Sale катары жүргүзүлбөйт. Өзүнчө LOSS SALE / LIQUIDATION (LSS) документи колдонулат.

Милдеттүү: OWNER гана түзөт/бекитет; себеп; товар жана саны; FIFO LOT Allocation; FIFO COGS; сатуу баасы; эсептелген жоготуу; кардар; дата; комментарий; Audit Log.

Формула: Loss = FIFO COGS − Final Selling Price (эгер Final Selling Price < FIFO COGS).

Бул жоготуу отчеттордо кадимки позитивдүү сатуу маржасы катары көрсөтүлбөйт.

LOSS SALE боюнча бонус эсептелбейт: Bonus Base = 0. Терс маржа сатуучунун башка сатууларынын бонус базасынан да кемитилбейт (OWNER өзү чечкен операция болгондуктан).

### 13.7. Скидканын бонус менен байланышы

Сатуучунун бонус базасы скидкадан кийинки фактический Revenue боюнча эсептелет:

Bonus Base = Revenue after Discount − FIFO COGS − Sale-specific adjustments/returns

Демек, скидка көбөйгөн сайын сатуу маржасы жана кызматкердин бонус базасы автоматтык азаят.

### 13.8. Скидка боюнча Audit Log

Ар бир кол менен берилген скидка үчүн кеминде: Sale; кызматкер; баштапкы автоматтык баа; Final Selling Price; скидка суммасы; скидка пайызы; FIFO COGS; сатуу маржасы; скидканын себеби; approval керекпи; ким бекитти; дата жана убакыт сакталат.

3. Төлөм
4. Сатууну ырастоо

CONFIRMED болгон Sale документи редакцияланбайт (§27.1); ката болсо Return же Correction/Reversal менен оңдолот.

## 15. Төлөм

Сатуу:

- толук төлөм;
- жарым төлөм + карыз;
- толугу менен карыз

болушу мүмкүн.

Төлөм бир нече каналга бөлүнүшү мүмкүн (mixed payment).

Мисалы, 2 000 KGS сатуу: 1 000 KGS накталай; 500 KGS MBank; 500 KGS O!Bank.

### 15.1. Накталай жана сдача

Эгер 2 200 KGS төлөнө турган болсо жана кардар 2 500 KGS берсе:

- кабыл алынган акча: 2 500;
- сатуу суммасы: 2 200;
- сдача: 300.

Сдача автоматтык эсептелет.

### 15.2. Сдача — Cash гана

Сдача накталай Cash эсебинен гана берилет. MBank, O!Bank, банктык же башка электрондук эсептен «сдача» операциясын жүргүзүүгө болбойт.

Мисал:

Sale Total = 8 000 сом; Customer Cash Given = 10 000 сом; Change = 2 000 сом; Net Cash Increase = 8 000 сом.

Система: кардар берген Cash суммасын; берилген сдачаны; кассага таза кирген сумманы өзүнчө эсептеп сактайт.

Эгер сатуучунун Cash кассасында сдачага жетиштүү акча жок болсо, система муну көрсөтөт. OWNER же башка кызматкердин кассасынан акча берилсе, ал Account Transfer (TRN) катары документтелип, андан кийин гана сатуучунун Cash кассасынан сдача берилет.

## 16. Кардардын карызы

Карызга сатууда:

- товар складдан чыгат;
- төлөнгөн сумма катталат;
- калган сумма кардардын карызына жазылат;
- төлөө мөөнөтү милдеттүү түрдө коюлат;
- жооптуу сатуучу сакталат.

Карыз статусу: Ачык; Жарым-жартылай төлөнгөн; Жабылган.

Карыздын мөөнөтүнө 3 күн калганда система жооптуу сатуучуга жана OWNER'ге эскертүү берет.

Кардар карызын жарым-жартылай төлөсө, калган сумма автоматтык жаңыланат.

## 16-А. Payment Allocation — кардар төлөмүн Sale'га байланыштыруу (жаңы)

Кардардын ар бир төлөмү (PAY) кайсы Sale'дын карызын канчага жапканын так сактайт.

### 16-А.1. Демейки эреже — FIFO

Кардардын бир нече ачык карызы болсо, төлөм демейки боюнча эң эски ачык карыздан баштап жабат (FIFO).

Мисал:

- SAL-101 карызы: 30 000 сом (эң эски);
- SAL-115 карызы: 20 000 сом;
- кардар төлөдү: 40 000 сом.

Автоматтык бөлүштүрүү: SAL-101 → 30 000 (жабылды); SAL-115 → 10 000 (калдыгы 10 000).

### 16-А.2. Кол менен бөлүштүрүү

Кардар же кассир конкреттүү Sale'ды көрсөтсө, төлөм ошол Sale'га багытталышы мүмкүн. Демейки тартиптен четтөө документте сакталат.

### 16-А.3. PAY документи

Ар бир кардар төлөмүндө кеминде: документ номери; кардар; жалпы сумма; төлөм каналы (Cash/MBank/O!Bank, mixed болсо ар бири); акча түшкөн эсеп; ар бир Sale боюнча жабылган сумма (Allocation lines); жооптуу кызматкер; дата жана убакыт сакталат.

### 16-А.4. Бонус менен байланыш

§23.2деги «Sale Outstanding = 0» шарты дал ушул Payment Allocation маалыматына таянып эсептелет. Демек кайсы Sale качан толук жабылганы дайыма так белгилүү.

### 16-А.5. Кардардын ашыкча төлөмү (жаңы)

Эгер кардардын төлөмү бардык ачык карыздарынан ашып кетсе (мис. карыз 18 000 сом, кардар 20 000 сом төлөдү), ашкан бөлүк жоголбойт жана «түшүнүксүз акча» болуп калбайт.

Эреже:

- карыздарды жапкан бөлүк — Payment Allocation боюнча Sale'дарга бөлүштүрүлөт;
- ашкан бөлүк — автоматтык түрдө Customer Advance (ADV) документи менен кардардын авансы болуп катталат (§17-А эрежелери боюнча милдеттенме);
- бул аванс кийинки сатууга колдонулат же кардар кааласа §17-А.4 тартибинде кайтарылат;
- система кассирге ашыкча төлөм болгонун ачык көрсөтөт жана кассир муну кардарга билдирет.

Walk-in Customer'ге ашыкча төлөм кабыл алынбайт — так сумма же сдача менен гана иштелет (§11.1.2, §15).

### 16.1. Кардардын кредиттик лимити

Ар бир кардар үчүн карызга сатууга уруксат берилген максималдуу сумма көзөмөлдөнөт.

Система эки деңгээлдеги лимитти колдойт:

- Category Default Credit Limit — Standard/Silver/Gold/VIP категориясы үчүн OWNER койгон демейки лимит;
- Individual Credit Limit — конкреттүү кардар үчүн OWNER койгон жеке лимит.

Эгер Individual Credit Limit бар болсо, ал категориялык демейки лимитти алмаштырат. Лимиттин суммалары настройкадан OWNER тарабынан башкарылат.

### 16.2. Жаңы карызга сатуудагы текшерүү

Система сатуу тастыкталганга чейин эсептейт:

Projected Debt = Current Open Debt + New Debt Amount

Шарт: Projected Debt ≤ Effective Credit Limit

New Debt Amount — жаңы сатуунун толук суммасы эмес, кардар азыр төлөбөй калган бөлүгү.

Мисал: товар = 100 000 сом; азыр төлөдү = 80 000 сом; жаңы карыз = 20 000 сом. Credit Limit'ке 100 000 эмес, 20 000 сом кошулат.

### 16.3. Лимит ашкан учурда

Мисалы: Effective Credit Limit = 100 000 сом; Current Open Debt = 70 000 сом; жаңы товар = 50 000 сом.

Кардар дагы максимум 30 000 сом жаңы карыз ала алат. Демек, 50 000 сомдук сатууну өткөрүү үчүн кардар кеминде 20 000 сом азыр төлөшү керек.

Эгер Current Open Debt + New Debt Amount > Credit Limit болсо, SALES MANAGER карызга сатууну тастыктай албайт.

### 16.4. Мөөнөтү өтүп кеткен карыз

Эгер кардардын кеминде бир OVERDUE карызы бар болсо:

- ага жаңы карызга сатуу автоматтык блоктолот;
- жаңы бронь түзүү да блоктолот (v2де кошулду);
- бирок кардар жаңы товарды толук төлөсө, ошол толук төлөнгөн сатуу блоктолбойт.

### 16.5. OWNER Override

Зарыл учурда OWNER төмөнкү блокторду атайын override кыла алат:

- Credit Limit ашып кетиши;
- OVERDUE карыз бар учурда жаңы карызга сатуу же бронь.

Override үчүн милдеттүү: OWNER авторизациясы; себеп/комментарий; дата жана убакыт; кардар; Current Open Debt; Overdue Amount; Effective Credit Limit; New Debt Amount; Projected Debt; байланышкан Sale/Reservation.

Override Audit Log'до өзгөртүлбөс тарых катары сакталат. Кадимки сатуучу бул блокту айланып өтө албайт.

### 16.6. Кредиттик контроль үчүн көрсөтүлүүчү маалымат

Кардар тандалганда сатуу экранында кеминде: Customer Type; Customer Category; Effective Credit Limit; Current Open Debt; Overdue Amount; Available Credit; эң эски төлөнбөгөн карыздын мөөнөтү көрүнөт.

Available Credit = max(0, Effective Credit Limit − Current Open Debt)

Эгер overdue карыз болсо, карызга сатуу үчүн Available Credit фактически 0 деп эсептелет, OWNER override кылмайынча.

### 16.7. Өзгөрбөс кредиттик эреже

Жаңы карызга сатууда система кардардын учурдагы ачык карызын, жаңы түзүлүүчү карызды, Effective Credit Limit'ти жана overdue карызын текшерет. Credit Limit ашса же overdue карыз бар болсо, карызга сатуу блоктолот. OWNER гана милдеттүү себеп менен override кыла алат. Толук төлөнгөн сатууга бул блок колдонулбайт.

## 17. Бронь (Reservation — RSV)

Товарды брондоого болот. Брондолгон товар башка кардарга сатылбайт.

Бронь аванс менен же 0 KGS аванс менен болушу мүмкүн.

Ар бир брондо аяктоо күнү жана аяктоо убактысы милдеттүү.

Мөөнөт өтсө: бронь автоматтык EXPIRED болот; товар кайра сатууга ачылат.

Кардар баш тартса, бронду мөөнөтүн күтпөй жокко чыгарууга болот.

### 17.1. Бронь баасы (жаңы)

Бронь документинде товардын баасы фиксацияланат (кардардын Type/Category боюнча бронь түзүлгөн учурдагы баа).

Бирок сатуу тастыкталганда §13.4 FIFO COGS блогу кайра текшерилет: эгер аралыкта өздүк нарк көтөрүлүп, фиксацияланган баа FIFO COGSтен төмөн болуп калса, сатуу кадимки тартипте тастыкталбайт — OWNER чечим кабыл алат (бааны оңдоо же LSS процесси).

### 17.2. Бронду жокко чыгаруу жана аванс (v2де такталды)

Демейки эреже: бронь жокко чыгарылса же мөөнөтү өтсө, алынган аванс кардарга толук кайтарылат.

Кошумча:

- система ар бир кардар боюнча cancel/expire статистикасын жүргүзөт (канча бронь түзгөн, канчасы сатыкка айланган, канчасы күйгөн);
- бул статистика OWNER'ге отчетто көрүнөт;
- OWNER келечекте настройкадан Cancellation Fee саясатын (мис. акыркы X саат ичинде баш тартса аванстын Y% кармалат) активдештире алат — баштапкы версияда (MVP) бул параметр өчүк турат, бирок архитектура даяр болот.

### 17.3. Reservation Abuse Control

Reservation товарды чексиз же көзөмөлсүз бекер бөгөттөө куралы болбошу керек. Reservation Policy'ни OWNER башкарат.

OWNER конфигурациялай алат:

- Advance Required Above Amount — кайсы суммадагы брондон баштап аванс милдеттүү;
- Minimum Advance % — минималдуу аванс пайызы;
- Max Active Reservations per Customer — бир кардарга бир убакта уруксат берилген активдүү брондордун максималдуу саны;
- Max No-Advance Reservation Hours — 0 KGS аванс менен брондун максималдуу мөөнөтү;
- Default Reservation Duration — кадимки брондун демейки мөөнөтү.

#### 0 KGS аванс менен бронь

Толук тыюу салынбайт, бирок мөөнөтү Max No-Advance Reservation Hours менен чектелет. Мөөнөт бүткөндө система ACTIVE → EXPIRED статусуна автоматтык өткөрөт жана ошол замат Reserved Stock'ту бошотот.

#### Аванс милдеттүү болгон бронь

Advance Required Above Amount чегинен жогору Reservation үчүн:

Required Advance = Reservation Amount × Minimum Advance %

Мисалы: чек = 20 000 KGS; Minimum Advance = 20%; Reservation Amount = 50 000 KGS → Required Advance = 10 000 KGS.

Талап кылынган аванс алынмайынча товар толук активдүү Reserved Stock катары бекитилбейт.

#### Product-level Reservation Rule

Кымбат же дефицит товар үчүн Product Card'да Reservation Advance Required = Yes/No эрежеси коюлушу мүмкүн. Product деңгээлинде аванс милдеттүү болсо, жалпы сумма чегине карабастан Reservation аванссыз активдештирилбейт. Керек болсо Product үчүн өзүнчө Minimum Advance % белгиленет.

#### Бир кардардын активдүү бронь лимити

Active Reservations ≤ Max Active Reservations per Customer

Лимитке жеткенде жаңы Reservation кадимки тартипте түзүлбөйт. Өзгөчө учур OWNER approval, милдеттүү reason жана Audit Log менен гана.

#### Walk-in Customer

Walk-in Customer үчүн Reservation жана Advance колдонулбайт.

#### Overdue кардар

Overdue карызы бар кардарга жаңы бронь түзүлбөйт (§16.4), OWNER override кылмайынча.

#### Reservation Audit

Система сактайт: Customer; salesperson; created date/time; expiration date/time; reservation amount; advance required; advance paid; reserved products/qty; фиксацияланган баа; status; cancelled/expired reason; OWNER override болсо reason; Audit Log.

OWNER отчеттон көрөт: активдүү брондор; 0 KGS аванс менен брондор; мөөнөтү өтүп кеткен брондор; бир кызматкер түзгөн брондордун саны; көп 0 KGS бронь түзгөн кызматкерлер; бронь аркылуу эң көп бөгөттөлгөн товарлар; кардарлар боюнча cancel статистикасы.

#### Катуу бронь эрежеси

Reservation товарды чексиз бекер бөгөттөй албайт. Мөөнөтү бүткөн бронь автоматтык EXPIRED болуп, Reserved Stock дароо бошотулат.

## 17-А. Кардардын авансы — киреше эмес, милдеттенме (ADV)

Бронь, алдын ала заказ же башка себеп менен товар кардарга фактически берилгенге чейин алынган акча сатуу кирешеси болуп эсептелбейт.

Негизги эреже:

Кардардан товар берилгенге чейин алынган аванс Cash/Bank'ты көбөйтөт жана ошол эле суммада «Кардарлардын авансы / Customer Advances» милдеттенмесин түзөт. Revenue жана COGS сатуу фактически тастыкталганда гана таанылат.

### 17-А.1. Аванс алынганда

Мисалы, кардар бронь үчүн 20 000 сом төлөдү:

Cash/Bank ↑ 20 000; Customer Advances ↑ 20 000; Sales Revenue = 0; COGS = 0; Profit = 0.

### 17-А.2. Сатуу аяктаганда авансты колдонуу

Мисалы: сатуу баасы 50 000; аванс 20 000; калган төлөм 30 000.

Сатуу тастыкталганда: Customer Advances ↓ 20 000; Cash/Bank ↑ 30 000; Sales Revenue ↑ 50 000; Inventory FIFO боюнча азаят; COGS FIFO боюнча таанылат.

### 17-А.3. Аванс + карызга сатуу

Товар 50 000, аванс 20 000, калганы карызга: Customer Advances ↓ 20 000; Sales Revenue ↑ 50 000; Customer Receivable ↑ 30 000; Inventory жана COGS FIFO боюнча.

### 17-А.4. Бронь жокко чыгарылып, аванс кайтарылганда (v2.1де такталды)

Финансылык натыйжа: Cash/Bank ↓ кайтарылган сумма; Customer Advances ↓ ошол сумма; Sales Revenue өзгөрбөйт; COGS түзүлбөйт; операциялык пайдага таасир жок.

Кошумча эрежелер:

- Карыз offset: эгер кардардын ачык карызы бар болсо, аванс алгач карызды азайтат (§35.4 логикасы): Cash Refund = Advance Amount − Debt Offset. Карыз жабылгандан ашкан бөлүк гана колго/эсепке кайтарылат.
- Refund булагы: акча кайсы эсептен чыгары §35.5теги приоритет менен аныкталат (алгач аванс түшкөн эсеп, андан кийин сатуучунун эсеби, андан кийин OWNER эсеби; булак өзгөрсө override reason милдеттүү).
- PIN: аванс кайтаруу — акча чыккан критикалык операция, ар дайым PIN Confirmation талап кылат (Security бөлүмү).

Кайтаруу кайсы аванс документине тиешелүү экени жана кайсы эсептен акча чыкканы сакталат.

### 17-А.5. Баланстагы өзүнчө статья

Баланс отчетунда өзүнчө «Кардарлардын авансы / Customer Advances» милдеттенме статьясы болушу керек.

Отчетто: мезгил башындагы калдык; жаңы алынган аванстар; сатууга колдонулган аванстар; кайтарылган аванстар; мезгил аягындагы калдык.

Customer Advances эч качан Customer Receivables менен бир статьяга аралаштырылбайт.

### 17-А.6. Аванс документи (ADV)

Ар бир аванс үчүн кеминде: документ номери; дата жана убакыт; кардар; бронь/заказ; сумма; валюта; төлөм ыкмасы; акча түшкөн эсеп; статус; сатууга колдонулган сумма; кайтарылган сумма; калган аванс; жооптуу кызматкер; комментарий.

Аванс статусу: ACTIVE; PARTIALLY_APPLIED; APPLIED; REFUNDED; CANCELLED.

## 18. Складдагы өздүк наркты эсептен чыгаруу — FIFO / партия (LOT)

EGOMOT товардык запастын өздүк наркын FIFO (First In, First Out) ыкмасы менен, партия (LOT) деңгээлинде жүргүзөт.

Өзгөрбөс негизги эреже:

Ар бир приход өзүнчө FIFO cost layer / LOT түзөт. Сатууда эң эски жеткиликтүү партия биринчи эсептен чыгарылат.

Ар бир LOT: сатып алуу/приход документи; приход датасы; товар; баштапкы саны; калган саны; бир даананын акыркы landed cost; партиянын жалпы наркын сактайт.

Бир эле товар ар башка партияларда ар башка өздүк нарк менен болушу мүмкүн. Система аларды орточолоштурбайт.

Мисал:

LOT №1: 10 мотор × 7 000 сом; LOT №2: 10 × 7 500; LOT №3: 10 × 8 000.

Кардарга 12 мотор сатылса, FIFO боюнча: LOT №1ден 10 × 7 000 = 70 000; LOT №2ден 2 × 7 500 = 15 000. COGS = 85 000 сом.

Складда калат: LOT №1: 0; LOT №2: 8 × 7 500 = 60 000; LOT №3: 10 × 8 000 = 80 000. Жалпы = 140 000 сом.

Сатуу документи ар бир сатылган позиция кайсы LOT'тон жана кандай өздүк нарк менен чыкканын сактайт. Бир сатуу бир нече LOT'ту камтышы мүмкүн.

### 18.0. Возврат FIFO эрежеси (v2де такталды)

Возврат болгондо товар баштапкы сатууда эсептен чыгарылган өздүк нарк менен, бирок бүгүнкү дата менен ЖАҢЫ FIFO layer катары складга кирет. Учурдагы же кийинки партиянын өздүк наркы колдонулбайт. Эски LOT'тун калдыгы кайра көбөйтүлбөйт.

Мисал: мотор LOT-001ден 7 000 сом менен сатылган; арадан 2 ай өтүп кайтарылды. Складга RET-LOT (жаңы layer, дата = бүгүн, cost = 7 000 сом) катары кирет. FIFO кезегинде ал бүгүнкү датасы боюнча турат.

Бул FIFO эрежеси складдын наркына, COGS'ка, маржага, возратка, ОПУга жана Баланска бирдей колдонулат.

### 18.1. Партия (LOT) — өз алдынча негизги складдык объект

Негизги принцип:

Purchase — сатып алуу документи. LOT — товар фактически кабыл алынып, landed cost эсептелген складдык партия. Бул экөө бир объект эмес.

Негизги байланыш:

Purchase → Receipt → LOT → LOT Items → Sale LOT Allocation → Return

#### 18.1.1. LOT негизги маалыматтары

Ар бир LOT кеминде: уникалдуу партия номери; байланышкан Purchase; байланышкан Receipt; заказ датасы; приход датасы; статус; жалпы товар салмагы; Кытай ичиндеги транспорттук чыгым; эл аралык cargo чыгымы; Кыргызстандагы ички транспорттук чыгым; башка түз логистикалык чыгымдар; приходдо колдонулган CNY/KGS курсу; приходдо колдонулган USD/KGS курсу; курстардын булагы (ФАКТИЧЕСКИЙ/REFERENCE/MANUAL); партиянын жалпы landed cost'у; жооптуу кызматкер; түзүлгөн жана тастыкталган дата/убакыт.

#### 18.1.2. LOT Items

Ар бир товар үчүн өзүнчө LOT Item: Product; заказ кылынган саны; фактически кабыл алынган саны; 1 даана салмагы; позициянын жалпы салмагы; Кытайдагы сатып алуу баасы; сатып алуу валютасы; бөлүштүрүлгөн Кытай ички транспорту; бөлүштүрүлгөн эл аралык cargo; бөлүштүрүлгөн Кыргызстан ички транспорту; башка бөлүштүрүлгөн түз чыгымдар; 1 даана акыркы landed cost; баштапкы саны; FIFO боюнча калган саны.

#### 18.1.3. LOT жана FIFO калдык

Бир эле товар бир убакта бир нече LOT'то, ар башка өздүк нарк менен болушу мүмкүн.

| LOT | Товар | Приход | FIFO калдык | 1 даана landed cost |
|---|---|---|---|---|
| LOT-001 | Мотор 70H | 20 | 0 | 7 000 сом |
| LOT-002 | Мотор 70H | 30 | 8 | 7 500 сом |
| LOT-003 | Мотор 70H | 20 | 20 | 8 000 сом |

10 мотор сатылса: LOT-002ден 8 × 7 500; LOT-003төн 2 × 8 000 FIFO боюнча эсептен чыгарылат.

Система жалпы товар калдыгын гана эмес, ар бир LOT Item боюнча калган санды да сактайт.

#### 18.1.4. Sale LOT Allocation

Ар бир сатылган позиция кайсы LOT'тон канча даана жана кандай өздүк нарк менен чыкканы өзүнчө байланыш катары сакталат:

- Sale Item → LOT-002: 8 даана × 7 500 сом;
- Sale Item → LOT-003: 2 даана × 8 000 сом.

Бул маалымат COGS, маржа, складдык нарк, FIFO, возврат жана аудит үчүн негизги булак.

#### 18.1.5. Возвраттын LOT менен байланышы

Возврат баштапкы Sale LOT Allocation'га байланышат. Кайтарылган товар баштапкы сатууда кайсы LOT'тон жана кандай өздүк нарк менен чыккан болсо, ошол тарых сакталат жана товар §18.0 боюнча ошол өздүк нарк менен жаңы FIFO layer катары кайра кирет.

#### 18.1.6. LOT боюнча өзгөрбөс эрежелер

1. Приход тастыкталмайынча LOT сатууга жеткиликтүү болбойт.
2. Ар бир кабыл алынган товар LOT Item'га байланышат.
3. LOT Item'дын landed cost'у приход тастыкталганда бекитилет.
4. Кийинки валюталык курстук айырма LOT'тун бекитилген landed cost'ун өзгөртпөйт.
5. Сатууда FIFO эң эски жеткиликтүү LOT Item'дан башталат.
6. Ар бир Sale Item үчүн LOT Allocation сакталат.
7. Возврат баштапкы Sale LOT Allocation тарыхына байланышат жана баштапкы cost, бүгүнкү дата менен жаңы layer түзөт.
8. LOT жана LOT Allocation тарыхы финансылык/складдык документтерди өчүрүү аркылуу жоголбоого тийиш.

## 19. Сатуучулардын кассалары жана эсептери

Ар бир сатуучуга өзүнчө эсептер ачылат.

OWNER: бардык эсептерди көрөт; эсеп түзөт; өзгөртөт; жабат; сатуучунун эсебинен кайсы борбордук/OWNER эсебине акча өткөрүлөрүн көрсөтөт.

Эсептер ортосундагы ар бир которуу Account Transfer (TRN) документи менен жүргүзүлөт: ким; кайсы эсептен; кайсы эсепке; канча; качан.

## 20. Күндү жана кассаны жабуу

Ар бир сатуучу күндүн жыйынтыгын жабат.

Система көрсөтөт: күндүк сатуу суммасы; накталай; MBank; O!Bank; карызга сатуу; кайтаруу; бронь/аванс; башка тиешелүү операциялар.

Сатуучу фактический акчаны система менен салыштырат. Айырма чыкса, себеби жазылат.

Күндүн бирдиктүү статус чынжыры (v2.1де бириктирилди):

OPEN → CASH_HANDED → DAY_CLOSED

Тартиби:

1. OPEN — күн ачык, операциялар жүрүп жатат.
2. CASH_HANDED — сатуучу күндүк жыйынтыкты салыштырып, OWNER көрсөткөн эсепке керектүү сумманы TRN документи менен өткөрдү. Айырма чыкса, себеби жазылып, документтелди.
3. DAY_CLOSED — Pre-check өтүп, күн жабылды. Ушундан кийин ошол датага эч кандай кадимки операция (TRN да) жүргүзүлбөйт.

Демек акча өткөрүү күн жабылганга чейин жүргүзүлөт — жабылган күнгө TRN документи түзүлбөйт.

Day Close алдындагы милдеттүү Pre-check жана Period Lock эрежелери өзүнчө бөлүмдө (Period Lock).

## 21. Склад үчүн айланма жоопкерчилик

Өзүнчө склад кызматкери жок болгондуктан, 3 сатуучу кезектешип склад үчүн жооп берет.

Мөөнөт OWNER тарабынан коюлат: 2 күн; 3 күн; 1 жума; же башка мөөнөт. Мөөнөт катуу жумага байланбайт.

### 21.1. Өткөрүп-кабыл алуу актысы (HND) — жеңилдетилген тартип (v2)

Жоопкерчиликти өткөрүүдө өткөрүп жаткан жана кабыл алып жаткан сатуучу товарды бирге текшерет.

Ар бир өткөрүүдө толук инвентаризация талап кылынбайт. Милдеттүү текшерүү:

- A-класс / кымбат товарлар (мотор, батарея, контроллер ж.б. — тизмени OWNER аныктайт) — толук саналат;
- рандом тандалган 10–15 позиция (система өзү тандап берет) — саналат;
- толук инвентаризация §22 боюнча өзүнчө графикте жүргүзүлөт.

Актта (HND): текшерилген товарлардын калдыгы; жалпы сумма/нарк; айырма; комментарий; өткөргөн адам; кабыл алган адам; дата/убакыт сакталат.

Жоопкерчилик акт эки тарап тарабынан ырасталмайынча кийинки сатуучуга өтпөйт.

Кытайдан жаңы партия келгенде OWNER кайсы сатуучу кабыл аларын дайындай алат.

## 22. Инвентаризация (INV)

Сатуучулар инвентаризацияны кезектешип жүргүзө алышат.

Толук инвентаризация кеминде айына 1 жолу (график OWNER настройкасында) жүргүзүлөт.

Инвентаризацияда: системадагы калдык; фактический калдык; айырма салыштырылат.

Айырма болсо акт түзүлөт жана жооптуу адам көрсөтүлөт. Айырманын складдык корректировкасы Inventory Adjustment документи менен, OWNER тастыктоосу аркылуу гана жүргүзүлөт.

LOT деңгээли (v2.1де такталды): Inventory Adjustment LOT деңгээлинде жүргүзүлөт.

Недостача: саноодо кайсы LOT'тон жетишпегени так аныкталса — ошол LOT'тон; аныкталбаса — FIFO боюнча эң эски жеткиликтүү LOT'тон эсептен чыгарылат. Списание наркы = ошол LOT'тун Unit Landed Cost'у. Недостача жоготуусу өзүнчө статьяга түшөт жана бонус базасына кирбейт.

Ашыкча (излишек): OWNER чечими жана документтелген себеп менен өзүнчө adjustment layer катары (болжолдуу/аныкталган нарк менен, OPENING LOT логикасына окшош) киргизилет.

## 23. Сатуучунун бонусу жана аны төлөө мөөнөтү

Сатуучунун негизги бонусу сатуу суммасынан эмес, сатуунун маржасынан эсептелет.

Негизги формула:

Bonus Base = Sale Revenue − FIFO COGS − Sale-specific adjustments/returns

Calculated Bonus = Bonus Base × Bonus Rate

Бонус пайызы OWNER тарабынан настройкада башкарылат.

### 23.1. Бонус качан эсептелет?

Бонус сатуу тастыкталган учурда дароо эсептелет, бирок бул кызматкерге ошол замат төлөнөт дегенди билдирбейт.

Сатуу тастыкталганда: Revenue бекитилет; FIFO COGS белгилүү болот; маржа эсептелет; бонус эсептелет; статус CALCULATED.

Мисал: Revenue = 100 000; FIFO COGS = 70 000; Bonus Base = 30 000; Rate = 10%; Calculated Bonus = 3 000 сом.

Кардар али толук төлөй элек болсо, 3 000 сом төлөнүүгө даяр эмес.

### 23.2. Бонус качан төлөнүүгө даяр болот?

Бонус ошол конкреттүү сатуу боюнча кардардын карызы толук жабылганда гана PAYABLE статусуна өтөт.

Шарт: Sale Outstanding Amount = 0 (§16-А Payment Allocation маалыматы боюнча аныкталат).

Кардардын башка, мурдагы сатууга тиешелүү карызы бул конкреттүү сатуу боюнча бонус төлөөнү автоматтык блоктобойт.

Демек: сатуу болду → CALCULATED; ошол Sale толук төлөндү → PAYABLE; бонус берилди → PAID.

### 23.3. Бонус статустары

- CALCULATED — эсептелди, сатуу толук төлөнө элек;
- PAYABLE — сатуу толук төлөндү, бонус даяр;
- PAID — фактически төлөндү (BON документи менен);
- ADJUSTED — корректировкаланды;
- REVERSED — толук тескери эсептелди.

Бонус төлөмү өзүнчө Bonus Payment (BON) документи менен жүргүзүлөт жана кайсы Cash/Bank/кошелектен төлөнгөнү сакталат.

### 23.4. Возврат болгондогу бонус

Возврат болсо, кайтарылган товарга тиешелүү бонус да тескери эсептелет. Система original Sale жана анын FIFO / Sale LOT Allocation маалыматтарын колдонот.

Эгер бонус али төлөнө элек болсо: CALCULATED же PAYABLE сумма тиешелүү өлчөмдө азайтылат; толук возврат болсо толук REVERSED болушу мүмкүн.

Эгер бонус мурда PAID болсо: мурдагы төлөм өчүрүлбөйт; өзүнчө Bonus Adjustment түзүлөт; ашыкча төлөнгөн бонус кийинки бонустан эсептешүүгө алынат же OWNER бекиткен башка тартипте жабылат; бардык өзгөртүү аудитте.

### 23.5. Курстук айырма бонус базасына кирбейт

Поставщикке же каргого кийин төлөгөндө чыккан FX Gain/Loss сатуучунун бонусуна таасир бербейт.

Бонус үчүн сатуу учурунда бекитилген: Sale Revenue; FIFO COGS; сатууга түз тиешелүү возврат/корректировкалар гана колдонулат.

Supplier/Cargo FX Gain/Loss → Bonus Base'ге кирбейт. Кийинки курс өзгөрүшүнөн улам мурдагы маржа жана бонус кайра эсептелбейт.

Claim боюнча списаниелер (§8.5) да бонус базасына кирбейт.

### 23.6. Бонус боюнча аудит

Ар бир бонус жазуусунда кеминде: кызматкер; Sale; Sale Revenue; FIFO COGS; Bonus Base; Bonus Rate; Calculated Bonus; adjustment/reversal суммасы; final payable amount; статус; эсептелген дата; PAYABLE болгон дата; төлөнгөн дата; төлөм чыккан эсеп; байланышкан Return/Adjustment.

## 24. План жана KPI

OWNER айлык/мезгилдик план коё алат: жалпы сатуу; жалпы маржа/пайда; жаңы кардарлар; башка KPI.

Система план аткарылышын пайыз менен көрсөтөт.

Сатуучу боюнча: сатуу суммасы; пайда; орточо чек; жаңы кардарлар; план аткарылышы; эсептелген бонус көрүнөт.

## 25. Айлык акы (SLR)

OWNER ар бир кызматкерге өзүнчө айлык коё алат.

Кызматкер боюнча: негизги айлык; бонус; аванс; башка кошумча төлөм; кармоо (мыйзамдуу/бекитилген болсо); төлөнө турган жалпы сумма; төлөнгөн сумма сакталат.

Ар бир айлык төлөмү Salary Payment (SLR) документи менен жүргүзүлөт: кызматкер; мезгил; сумма; кайсы эсептен; дата; ким тастыктады.

Айлык төлөмдөрдүн тарыхы сакталат. Айлык — операциялык чыгым (OWNER withdrawal менен эч качан аралаштырылбайт, §3.1.6).

## 26. Операциялык чыгымдар (EXP)

Системада операциялык чыгымдарды киргизүү модулу болот.

Категориялардын мисалдары: склад арендасы; интернет; канцтовар; коммуналдык төлөмдөр; кызматкерлердин айлыгы; маркетинг; салык; жергиликтүү майда транспорт; башка операциялык чыгымдар.

Ар бир чыгымда: дата; категория; сумма; кайсы эсептен төлөндү; комментарий; ким киргизди; документ сакталат.

Партияга түз тиешелүү логистикалык чыгымдар бул модулга кирбейт — алар landed cost'ко allocation аркылуу кошулат (§9). Партияга байланышпаган майда транспорт гана OPEX болот.

Келечекте категория боюнча айлык бюджет/лимит коюп, ашып кетсе эскертүү берсе болот.

### 27.1. CONFIRMED документтин өзгөрбөстүгү (жаңы, ачык эреже)

Тастыкталган (CONFIRMED) финансылык же складдык документ — күн али ачык болсо да — түз редакцияланбайт жана өчүрүлбөйт.

Ката табылса:

- сатуу боюнча — Return (RET) же ошол эле күнү Correction/Reversal (COR);

DRAFT абалындагы документти оңдоого/өчүрүүгө болот — ал али финансылык таасир жарата элек.

## 35. Кайтаруу (Return — RET) — жаңы товар

Кайтаруу жөн гана товарды складга кайра кошуу эмес. Ал баштапкы сатууга байланышкан тескери операция катары жүргүзүлөт. Максат — склад, касса, кардар карызы, сатуу кирешеси, өздүк нарк жана пайда бир убакта туура оңдолушу.

### 35.1. Негизги эрежелер

1. Кайтаруу сөзсүз баштапкы сатууга байланышат — эч кандай exception жок (Walk-in үчүн да, §11.1.4).
2. Баштапкы сатуу өчүрүлбөйт жана өзгөртүлбөйт.
3. Ар бир кайтарууга өзүнчө Возврат документи (RET) түзүлөт.
4. Толук жана жарым-жартылай (частичный) кайтаруу колдоого алынат.
5. Колдонулбаган, кайра сатууга жарактуу товар гана кадимки складга кайтарылат.
6. Кайтарылган товар баштапкы сатуудагы өздүк нарк менен, бүгүнкү дата менен жаңы FIFO layer катары кирет (§18.0).
7. Кайтаруу операциясы отчетторду автоматтык оңдойт.

### 35.2. Кайтаруу процесси

1. Сатуучу же OWNER баштапкы сатууну табат (чек номери, дата, товар, сумма боюнча издөө).
2. Кайтарылуучу товарды тандайт.
3. Кайтарылуучу санын көрсөтөт.
4. Кайтаруунун себебин көрсөтөт.
5. Система товар кайра сатууга жарактуубу же бракпы деп бөлөт.
6. Кайтарылуучу сумма эсептелет (original selling price боюнча).
7. Кардардын учурдагы карызы текшерилет.
8. Акчаны кайтаруу же карызды азайтуу жүргүзүлөт.
9. Товар тиешелүү складга кирет (жарактуу → MAIN, брак → DEFECT).
10. Возврат документи тастыкталат жана финансылык/складдык отчеттор жаңыланат.

### 35.3. Складга кайтаруу

Эгер товар жаңы, колдонулбаган жана кайра сатууга жарактуу болсо:

- MAIN складга §18.0 боюнча жаңы FIFO layer катары кирет;
- складдагы саны көбөйөт;
- складдык наркы баштапкы сатууда чыккан өздүк нарк менен калыбына келет.

Мисал: мотордун сатуудагы өздүк наркы — 7 000 сом; кийин башка партиянын наркы өзгөргөн; ошол мотор кайтарылса, складга 7 000 сом өздүк нарк менен (жаңы layer, бүгүнкү дата) кирет.

### 35.4. Карыз менен эсептешүү приоритети

Кайтарылуучу сумма биринчи кезекте кардардын ачык карызын азайтат:

Cash Refund = Return Amount − Debt Offset

Мисал: кайтаруу суммасы 10 000 сом; кардардын карызы 7 000 сом → карыз 0 болот; калган 3 000 сом кардарга кайтарылат.

Эгер карыз кайтаруу суммасынан чоң болсо, кардарга акча берилбейт; кайтаруу суммасы толугу менен карызды азайтат.

Debt Offset кайсы Sale'дардын карызын жапканы §16-А Payment Allocation принциби менен (эң эскиден баштап) сакталат.

### 35.5. Акчаны кайтаруу — кайсы эсептен

Возвратта кардарга фактически кайтарылуучу акча кайсы Payment Account'тан чыкканы сөзсүз документтелет.

Приоритет:

1. Original Payment Source — мүмкүн болсо акча баштапкы сатууда колдонулган төлөм ыкмасы/эсебинен кайтарылат;
2. баштапкы эсептен мүмкүн эмес болсо — возвратты жүргүзгөн сатуучунун тиешелүү Cash/MBank/O!Bank эсеби;
3. ал эсепте жетишсиз болсо — OWNER'дин тиешелүү компаниялык эсеби;
4. original payment source'тан башка эсеп колдонулса, Refund Source Override Reason милдеттүү сакталат.

Возврат бир нече эсепке бөлүнүп кайтарылышы мүмкүн (split refund).

Мисал: Original Sale төлөмү Cash 20 000 + MBank 30 000 болсо, толук возвратта мүмкүн болушунча Cash refund = 20 000; MBank refund = 30 000. Ар бир refund бөлүгү өзүнүн Payment Account кыймылын түзөт.

### 35.6. Возврат үчүн эсеп жетишсиз болсо

Эгер тандалган Payment Account'та refund үчүн акча жетишсиз болсо: система эскертет; башка уруксат берилген эсеп тандалат; же OWNER account колдонулат; бир нече эсептен split refund жүргүзүүгө болот.

Башка кассадан акча алуу жашыруун жүргүзүлбөйт. Кассалар ортосунда акча которулса, ал өзүнчө Account Transfer (TRN) документи менен жүргүзүлөт.

### 35.7. Частичный возврат

Бир сатуудагы товарлардын бир бөлүгүн гана кайтарууга болот.

Мисал: сатууда 10 мотор; кардар 2 моторду кайтарды → баштапкы сатуу толугу менен жокко чыгарылбайт; 2 мотор боюнча гана возврат түзүлөт; 2 мотордун кирешеси жана өздүк наркы гана тескери эсептелет; 2 мотор гана складга кирет.

Бир товар боюнча кайтарылган жалпы сан баштапкы сатылган сандан ашпоого тийиш — система муну катуу текшерет.

### 35.8. Финансылык жана отчеттук таасир

Возврат тастыкталганда система автоматтык:

- сатуу кирешесин кайтарылган суммага азайтат;
- кайтарылган товардын COGS'ун тескери эсептейт;
- складдын санын жана наркын калыбына келтирет;
- кардардын карызын тиешелүү суммага азайтат;
- реалдуу акча кайтарылса, тиешелүү касса/банк эсебин азайтат;
- сатуу маржасын, пайданы жана бонусту (§23.4) кайра эсептейт;
- ДДС, ОПУ жана Баланска туура таасир берет;
- кардар категориясынын эсептөө базасын азайтат (§12.1).

Возврат баштапкы сатууну тарыхтан өчүрбөйт. Баштапкы сатуу жана возврат өзүнчө документтер болуп сакталат.

### 35.9. Возврат документи (RET)

Документте кеминде: документ номери; дата жана убакыт; кардар; баштапкы сатуу; товар; кайтарылган саны; баштапкы сатуу баасы; баштапкы өздүк наркы; кайтаруунун себеби; кайтаруу түрү (толук/частичный); товар кайра сатууга жарактуубу; кардардын карызынан канча сумма эсептелди; кардарга канча акча кайтарылды; акча кайсы эсептен кайтарылды; товар кайсы складга кирди; операцияны ким түздү жана ким тастыктады; комментарий.

### 35.10. Refund Audit

Ар бир акчалай возврат үчүн кеминде: Return документ; Original Sale; Original Payment Source; фактически колдонулган Refund Payment Account; refund amount; Debt Offset; split refund болсо ар бир бөлүгү; original source өзгөрсө override reason; операцияны жүргүзгөн кызматкер; OWNER approval, эгер талап кылынса; дата жана убакыт сакталат.

### 35.11. Брак товар

Эгер кайтарылган товар брак деп тастыкталса, ал кадимки складга кирбейт. Ал DEFECT складына өткөрүлүп, §36–38-бөлүмдөрдөгү процесс боюнча жүргүзүлөт.

Наркы (v2.1де такталды): брак товар DEFECT складга баштапкы сатуудагы FIFO COGS менен кирет (жарактуу возврат сыяктуу эле, §18.0 принциби) жана списаниеге (WOF) чейин ошол нарк менен турат. §38деги «списаниедеги өздүк нарк» дал ушул нарк.

## 36. Колдонулган товар жана брак

Негизги саясат:

Колдонулган товар кадимки шартта кайтарылбайт. Заводдук/тастыкталган брак болсо, кепилдик шарттарынын ичинде возврат кабыл алынат.

Бракта кардарга: акчаны толук кайтаруу; же жаңы товарга алмаштыруу варианты болушу мүмкүн.

Эгер кардардын карызы болсо: кайтарылуучу сумма биринчи карызын азайтат (§35.4); калган сумма болсо гана кардарга кайтарылат.

Брак боюнча акт (DEF) милдеттүү.

### Алмаштыруу (Exchange)

Брак товарды жаңыга алмаштыруу системада эки операция катары жүргүзүлөт:

- брак возврат (RET, товар DEFECT складга);
- жаңы сатуу (SAL, жаңы товар FIFO боюнча чыгат).

Эки документ бири-бирине байланышып сакталат. Баа айырмасы болсо кардар кошумча төлөйт же ага кайтарылат.

## 36-А. Кепилдик (Warranty) саясаты (жаңы)

### 36-А.1. Кепилдик мөөнөтү

Ар бир товар/категория үчүн OWNER Warranty Days параметрин коёт (мис.: мотор — 30 күн; контроллер — 14 күн; майда тетиктер — 0 күн; так сандар настройкада).

Кепилдик мөөнөтү сатуу тастыкталган датадан башталат.

### 36-А.2. Кепилдик текшерүү

Брак возврат түзүлгөндө система автоматтык текшерет:

Return Date ≤ Sale Date + Warranty Days

Мөөнөт ичинде болсо — брак возврат кадимки тартипте жүрөт.

Мөөнөт өтүп кетсе — кадимки кызматкер возвратты тастыктай албайт; OWNER гана милдеттүү себеп менен өзгөчө возвратты бекитет (Audit Log менен).

### 36-А.3. Кепилдик шарттары

Кепилдик заводдук бракка гана тиешелүү. Туура эмес колдонуудан, механикалык бузуудан, суудан/кыска туташуудан болгон бузулуу кепилдикке кирбейт — чечимди текшерүүдөн кийин жооптуу кызматкер/OWNER кабыл алат жана DEF актысында документтелет.

### 36-А.4. Брак боюнча Supplier Claim

Заводдук брак деп тастыкталган товар боюнча поставщикке SUPPLIER_CLAIM (CLM) түзүлүшү мүмкүн (§8.5).

Поставщик компенсацияласа (кийинки партияда товар же акча) — §8.7 логикасы менен жабылат. Компенсацияланбаса — брак §38 боюнча списаниеге кетет.

## 37. Брак кампасы (DEFECT)

Кардардан алынган брак товар кадимки сатылуучу складга кирбейт. Ал DEFECT складына кирет.

Брак товар кайра сатууга ачылбайт.

Брак боюнча маалымат: кайсы товар; саны; баштапкы сатуу; кардар; себеби; ким текшерди; дата; чечим (алмаштыруу / акча кайтаруу / Claim / списание) сакталат.

## 38. Бракты списание кылуу жана металлдан киреше

EGOMOTтун практикалык эрежеси:

Брак товарлар Кытайга кайра жөнөтүлбөйт. Алар топтолот жана кийин списание кылынат. Бирок алдын ала поставщикке Claim коюлушу мүмкүн (§36-А.4).

Процесс:

1. Брак товарлар DEFECT кампасында топтолот.
2. Ачык Supplier Claim бар болсо, анын тагдыры чечилет (компенсация же WRITTEN_OFF).
3. Списание актысы (WOF) түзүлөт.
4. Товарлар DEFECT кампасынан эсептен чыгарылат (өздүк наркы менен).
5. Товарлар ажыратылат.
6. Жез, алюминий жана башка металлдар өзүнчө сатылат.
7. Металл сатуудан түшкөн акча Other Income (OIN) документи менен системага киргизилет: сумма; акча түшкөн эсеп; байланышкан WOF актысы; ким кабыл алды; дата; комментарий.

Металл кирешеси өзүнчө статья менен катталат: Брак товарлардан түшкөн киреше.

OIN документи келечекте башка операциялык эмес кирешелерге да колдонулушу мүмкүн; ар бир OIN милдеттүү түрдө категория жана булак менен документтелет.

Отчетто: брак товарлардын эсептен чыгарылган өздүк наркы; металлдан түшкөн жалпы киреше; брак боюнча таза жоготуу көрүнөт.

Негизги формула:

Брак боюнча таза жоготуу = Списаниедеги өздүк нарк − Брактан/металлдан түшкөн киреше − Поставщиктен алынган компенсация

Брак жоготуулары сатуучулардын бонус базасына кирбейт.

## Security & Backup — минималдуу коопсуздук стандарты

EGOMOT'ту команда аз адам колдонсо да, ар бир операциянын ким тарабынан жасалганын аныктоо жана бизнес маалыматтарын жоготуудан коргоо милдеттүү.

### Жеке аккаунт

Ар бир кызматкер системага өзүнүн жеке аккаунту менен кирет.

Эрежелер:

- аккаунттарды кызматкерлер бири-бири менен бөлүшпөйт;
- ар бир операция учурдагы authenticated user менен байланышат;
- кызматкер иштен кетсе же доступ керек болбой калса, аккаунт өчүрүлбөйт — Inactive/Blocked кылынат;
- тарыхтагы документтер ошол кызматкерге байланышы менен сакталат;
- OWNER колдонуучуларды активдештирүү/блоктоо укугуна ээ.

### PIN Confirmation (v2де шарттуу болду)

Күнүмдүк жөнөкөй навигацияда PIN кайра-кайра суралбайт.

Критикалык операцияны акыркы жолу тастыктоодо учурдагы колдонуучу өзүнүн PIN'и менен кайра идентификацияланат.

PIN ар дайым талап кылынат:

- Return Confirmation;
- Write-off Confirmation;
- Advance Refund (аванс кайтаруу);
- Day Close;
- Correction/Reversal;
- Inventory Adjustment тастыктоо.

Sale Confirmation үчүн PIN шарттуу — төмөнкү учурлардын биринде гана суралат (параметрлер OWNER настройкасында):

- кол менен скидка берилгенде;
- карызга сатууда;
- сатуу суммасы белгиленген порогдон (мис. 50 000 KGS) жогору болгондо.

Кадимки, толук төлөнгөн, скидкасыз майда сатууда PIN суралбайт — сатуу тез бойдон калат (§1, §14 принциптери).

PIN confirmation:

- учурдагы authenticated user'ге тиешелүү болушу керек;
- башка кызматкердин PIN'ин колдонуу кадимки workflow болуп эсептелбейт;
- PIN Audit Log'го ачык текст түрүндө жазылбайт;
- система PIN verification ийгиликтүү/ийгиликсиз болгон фактыны гана сактайт.

PIN туура эмес болсо критикалык операция тастыкталбайт.

OWNER кийин кошумча критикалык операцияларга PIN талап кылууну конфигурациялай алат.

### Security / Login Log

Audit Log'дон өзүнчө Security Log жүргүзүлөт.

Security Log кеминде: successful login; failed login; logout; session/security окуялары; user; date/time; мүмкүн болгон учурда device/browser маалыматы; мүмкүн болгон учурда IP/техникалык connection маалыматы сакталат.

Максаты — кайсы аккаунт системага качан киргенин жана authentication боюнча шектүү окуяларды аныктоо.

### Audit Log жана Security Log айырмасы

Security Log — системага кирүү жана authentication тарыхы. Audit Log — системанын ичинде жасалган бизнес аракеттеринин тарыхы.

Мисалы:

- Security Log: Азамат → LOGIN → 09:03
- Audit Log: Азамат → SAL-2026-000125 → SALE_CONFIRMED → 09:17

Экөө тең өзүнчө сакталат жана бири-бирин толуктайт.

### Daily Automatic Backup

EGOMOT database күнүнө кеминде 1 жолу автоматтык backup кылынат.

Backup:

- автоматтык түзүлөт;
- timestamp менен сакталат;
- негизги production database/server менен бир эле failure point'та гана сакталбашы керек;
- мүмкүн болушунча өзүнчө коопсуз storage/location'до сакталат;
- backup ийгиликтүү же ийгиликсиз болгону журналга жазылат.

Backup failure болсо OWNER'ге notification/alert берилет.

### Restore Test

Backup бар экенин гана текшерүү жетишсиз. Мезгил-мезгили менен backup'тан database'ты калыбына келтирүү — Restore Test жүргүзүлөт.

Restore Test кеминде текшерет: backup файл жеткиликтүүбү; database калыбына келеби; негизги таблицалар ачылабы; критикалык маалыматтар окулуп жатабы.

Restore Test production database'ты үстүнөн жазуу жолу менен жүргүзүлбөйт; коопсуз тесттик чөйрө колдонулат.

### Backup Audit

Система/инфраструктура сактайт: backup created at; backup status; backup location/reference; backup size мүмкүн болсо; failure reason; акыркы successful backup; акыркы restore test; restore test result.

OWNER акыркы ийгиликтүү backup качан жасалганын көрө алышы керек.

### Катуу коопсуздук эрежелери

1. Ар бир кызматкердин жеке аккаунту болот.
2. Аккаунт бөлүшүүгө болбойт.
3. Return, Write-off, Advance Refund, Day Close, Correction/Reversal, Inventory Adjustment PIN талап кылат; Sale — шарттуу тартипте.
4. PIN ачык текст түрүндө журналда сакталбайт.
5. Login/Security Log Audit Log'дон өзүнчө жүргүзүлөт.
6. Database күнүнө кеминде бир жолу автоматтык backup кылынат.
7. Backup негизги production database менен бир гана failure point'ка көз каранды болбошу керек.
8. Backup failure OWNER'ге билдирилет.
9. Backup мезгил-мезгили менен Restore Test аркылуу текшерилет.
10. Тарыхтагы security/audit маалыматтары кадимки колдонуучу тарабынан өчүрүлбөйт.

### Негизги эреже

EGOMOT интернет байланышы менен гана операция жүргүзөт. Offline data entry жана кийин synchronization кылуу баштапкы версиянын (MVP) scope'уна кирбейт.

Интернет жок учурда маалымат өзгөртүүчү операцияларды түзүүгө же тастыктоого болбойт.

Бул, анын ичинде: Sale; Payment; Purchase; Receipt; Return; Reservation/Advance; Expense; Warehouse Transfer; Inventory Adjustment; Write-off; Supplier/Cargo Payment; Currency Exchange; Account Transfer; Correction/Reversal; Day/Month Close операцияларына тиешелүү.

### Интернет операция учурунда үзүлсө

Эгер интернет документти жөнөтүү же тастыктоо учурунда үзүлүп калса, frontend операция ийгиликтүү болду деп өз алдынча эсептебейт.

Негизги принцип:

Server Confirmation алынмайынча операция SUCCESS болуп эсептелбейт.

Интернет кайра келгенде система серверден документтин чыныгы статусун текшериши керек. Колдонуучу ошол эле операцияны сокур түрдө кайра-кайра жөнөтпөшү керек.

Бул duplicate Sale, Payment, Receipt, stock movement, financial posting пайда болуу коркунучун азайтат.

Маанилүү write/confirm операциялары техникалык жактан duplicate request'тен корголууга тийиш (idempotency key принциби).

### Offline Mode scope'ко кирбейт

Баштапкы версия ичинде: offline Sale; offline Payment; offline Receipt; локалдык кезекке документ топтоо; интернет келгенде автоматтык synchronization; offline conflict resolution ишке ашырылбайт.

Эгер келечекте Offline Mode керек болсо, ал өзүнчө версия/фаза катары synchronization, document identity, FIFO/stock conflict, cash/payment conflict жана audit эрежелери менен долбоорлонот.

### Катуу Online-only эрежеси

Mobile-first ≠ Offline-first. EGOMOT — Online-only. Сервер тастыктабаган маалымат өзгөртүүчү операция аяктаган операция катары көрсөтүлбөйт жана offline synchronization колдонулбайт.

## Period Lock — күндү жана айды жабуу эрежеси

Финансылык, складдык жана операциялык тарыхтын ишенимдүүлүгүн сактоо үчүн система жабылган күндөрдү жана айларды артка карай түз өзгөртүүгө жол бербейт.

Мезгилдин негизги статустары (§20 менен бирдиктүү чынжыр):

OPEN → CASH_HANDED → DAY_CLOSED → MONTH_CLOSED

### Business Date аныктамасы (жаңы)

Система операциянын экономикалык датасын (Business Date) жана системага киргизилген убакытты (Created Date/Time) өзүнчө сактайт.

Эрежелер:

- убакыт алкагы: Кыргызстан убактысы (Бишкек);
- Business Date демейки боюнча = документ түзүлгөн календардык күн;
- күн Day Close документи менен жабылганга чейинки бардык операциялар ошол business date'ке тиешелүү болот (түн жарымынан кийин, бирок күн жабыла электе жасалган операция мурунку business date'ке жазылышы мүмкүн — система муну ачык көрсөтөт);
- жабылган датага жаңы документ кадимки тартипте түзүлбөйт.

### Күн жабуу

Күн жабылгандан кийин ошол дата кадимки кызматкерлер үчүн LOCKED болуп эсептелет.

Жабылган күнгө кадимки жол менен: Sale; Payment; Expense; Purchase; Receipt; Return; Warehouse Transfer; Write-off; Inventory Adjustment; Advance; Reservation; Currency Exchange; башка финансылык же складдык документ артка дата менен кошулбайт, түз өзгөртүлбөйт жана өчүрүлбөйт.

### Day Close Pre-check — күндү жабуунун милдеттүү шарты

Күндү DAY_CLOSED статусуна өткөрөр алдында система автоматтык pre-check жүргүзөт.

Негизги шарттар:

- Unresolved Documents = 0 — бүтпөгөн документ жок;
- Cash Handover аткарылды — ар бир иштеген сатуучу күндүк кассасын салыштырып, талап кылынган сумманы TRN менен өткөрдү (CASH_HANDED статусу).

Экөө тең аткарылганда гана күн DAY_CLOSED болот.

Блоктоочу документтерге, анын ичинде: DRAFT Sale; DRAFT/Incomplete Payment; DRAFT Receipt; DRAFT Return; DRAFT Expense; DRAFT Write-off; DRAFT Inventory document; DRAFT Warehouse Transfer; SENT, бирок RECEIVED боло элек Warehouse Transfer; аяктабаган Advance/Reservation операциясы (статусу ошол күндүн жабылышын талап кылса); башка unresolved/open документтер кирет.

Day Close блоктолсо, система OWNER'ге жана тиешелүү жооптуу кызматкерге конкреттүү документтердин тизмесин көрсөтөт.

Мисалы:

- SAL-2026-000125 — DRAFT;
- RCV-2026-000018 — DRAFT;
- TRF-2026-000008 — SENT / not received.

Ар бир unresolved документти ачып: тастыктоо/аяктоо; тиешелүү финалдык статуска өткөрүү; же мыйзамдуу негизде CANCEL кылуу керек. Андан кийин Pre-check кайра жүргүзүлөт.

Документти күндү жабуу үчүн гана жашырууга, өчүрүүгө же статусун негизсиз өзгөртүүгө болбойт.

Катуу эреже: unresolved/open документ бар учурда OWNER да кадимки Day Close аркылуу текшерүүнү bypass кыла албайт. Алгач документ чечилиши керек.

### Жабылган күндөгү катаны оңдоо

Эгер жабылган күндө ката табылса, баштапкы документ үнсүз редакцияланбайт.

Оңдоо Correction / Reversal Document (COR) аркылуу жүргүзүлөт. Мындай операцияны OWNER гана тастыктай алат.

Correction/Reversal кеминде: Correction Document Number; Original Document ID жана Document Number; Original Business Date; Correction Effective Date; Correction Created Date/Time; Correction Type; Correction Reason; эски мааниси; жаңы/оңдолгон мааниси; финансылык таасири; складдык таасири; түзгөн колдонуучу; тастыктаган OWNER; Audit Log сакталат.

Original Document өчүрүлбөйт жана тарыхта калат.

### Business Date жана Created Date мисалы

31-август жабылган. 2-сентябрда августтагы ката табылды.

Correction документинде:

- Business/Effective Date — операция кайсы мезгилге тиешелүү экенин;
- Created Date/Time — коррекция системага чындап качан киргизилгенин

өзүнчө көрсөтөт. Audit тарыхы эч качан артка өзгөртүлбөйт.

### Ай жабуу

Ай толук текшерилип бүткөндөн кийин OWNER аны MONTH_CLOSED статусуна өткөрөт.

Ай жабылар алдында кеминде текшерилет: Cash/Bank, валюталык кассалар жана кызматкерлердин эсептери; Sales жана Payments; Customer Receivables; Customer Advances; Supplier/Cargo Payables; Supplier Receivables жана Claims; Purchases жана Receipts; Warehouse Stock жана FIFO LOT balances; Returns/Defects/Write-offs; Operating Expenses; Owner/Investor capital movements; Currency Exchange операциялары; Cash Flow; P&L; Balance.

MONTH_CLOSED болгон мезгилдеги документтер түз редакцияланбайт же өчүрүлбөйт. Жабылган айдын отчеттук тарыхы кийин кадимки операция менен үнсүз өзгөрүп кетпеши керек.

### Closed Period Correction

Жабылган айга тиешелүү ката табылса:

- кадимки кызматкер өзгөртүү киргизе албайт;
- OWNER гана Correction/Reversal процессин баштай алат;
- Original Document сакталат;
- себеп милдеттүү;
- өзгөрүүнүн мурдагы жана жаңы мааниси сакталат;
- бардык финансылык/складдык таасир документтелет;
- толук Audit Log түзүлөт.

### Period Reopen

Жабылган айды кайра OPEN кылуу күнүмдүк оңдоо ыкмасы эмес.

REOPEN өзгөчө кырдаалда гана: OWNER тарабынан; милдеттүү Reopen Reason менен; дата/убакытты сактоо менен; ким ачканын көрсөтүү менен; Audit Log менен жүргүзүлөт.

Ай кайра жабылганда кайра жабуу фактысы да Audit Log'до сакталат.

### Historical Data Migration

EGOMOT'ко тарыхый маалыматтар киргизилип жаткан учурда Period Lock маалыматтар толук текшерилгенге чейин колдонулбайт.

Тартип:

Historical Import → OPENING LOT / Ачылыш баланстары → Reconciliation → Cash/Stock/AR/AP/Capital текшерүү → Reports текшерүү → OWNER Approval → Period Close

Тарыхый ай жабылгандан кийин ал кадимки CLOSED PERIOD эрежелерине өтөт.

### Катуу Period Lock эрежеси

Жабылган күнгө же айга документти түз өзгөртүүгө, өчүрүүгө же кадимки жол менен артка дата коюп жаңы документ киргизүүгө болбойт. Ката Correction/Reversal (COR) документи аркылуу гана оңдолот. Жабылган мезгилге тиешелүү өзгөчө операция OWNER уруксаты, милдеттүү себеп жана толук Audit Log менен жүргүзүлөт.

## Document Numbering Standard — документтерди номерлөө системасы

Бардык бизнес-документтердин номери бирдиктүү борбордук стандарт боюнча автоматтык түзүлөт.

Негизги формат:

PREFIX-YYYY-NNNNNN

Мисал: SAL-2026-000125

Бул жерде: PREFIX — документтин түрү; YYYY — документ түзүлгөн жыл; NNNNNN — ошол документ түрүнүн жыл ичиндеги ырааттуу номери.

### Номер берүү эрежелери

1. Документ номерин система автоматтык берет.
2. Колдонуучу документ номерин кол менен түзбөйт жана өзгөртпөйт.
3. Ар бир документ түрүнүн өзүнчө sequence'и болот.
4. Sequence жыл боюнча жүргүзүлөт.
5. Жаңы календардык жыл башталганда ошол документ түрүнүн sequence'и 000001ден башталат.
6. Бир берилген документ номери эч качан башка документке кайра колдонулбайт.
7. Документ CANCELLED / VOIDED болсо да анын номери тарыхта сакталат.
8. Өчүрүлгөн же жокко чыгарылган номердин орду кайра толтурулбайт.
9. Номер түзүүдө duplicate болбошу database деңгээлинде да камсыздалат.
10. Бир убакта бир нече кызматкер документ түзсө да duplicate номер пайда болбошу керек.

Мисал: SAL-2026-000125 түзүлдү → кийин жокко чыгарылды → кийинки Sale → SAL-2026-000126. SAL-2026-000125 кайра колдонулбайт.

### Document Number жана Database ID

Document Number database primary key болуп эсептелбейт.

Ар бир документте: ички уникалдуу id (системалык UUID/ID); адам окуй турган documentNumber өзүнчө сакталат.

Интеграция, байланыштар жана database foreign key үчүн ички ID колдонулат; интерфейс, чек, отчет жана издөөдө Document Number колдонулат.

### Келечектеги филиалдар

Баштапкы версияда PREFIX-YYYY-NNNNNN форматы колдонулат.

Архитектура кийин филиал/Business Entity кодун кошууга мүмкүнчүлүк бериши керек: SAL-BSH-2027-000125; SAL-OSH-2027-000001.

Бирок филиалдар ишке кирмейинче азыркы жөнөкөй номерлөө форматы өзгөртүлбөйт.

### Документтер ортосундагы байланыш

Ар бир документ өзүнүн номерине ээ болот жана байланышкан документтердин ID/номерлерин сактай алат:

- PUR → RCV → LOT;
- SAL → PAY → RET;
- RCV → DIF → CLM;
- RSV → ADV → SAL;
- CEX → SPY / CPY.

Ошентип аудит учурунда операциянын толук документтик чынжырын көрүүгө болот.

### Өзгөрбөс номерлөө эрежеси

Бардык бизнес-документтер PREFIX-YYYY-NNNNNN стандарты менен автоматтык номерленет. Номер уникалдуу, кол менен өзгөртүлбөйт жана бир жолу берилгенден кийин эч качан кайра колдонулбайт. CANCELLED/VOIDED документ өз номери менен тарыхта калат.
